# Коммуникации SkeekS CMS: архитектура, решения и план

Единый документ проекта «коммуникации в CRM»: почта, мессенджеры, уведомления
клиентам, рассылки, КП, ИИ. Согласован с владельцем (октябрь 2026). Чтобы
продолжить работу в новом чате, достаточно прочитать этот файл, затем
`AGENTS.md` и `README.md` пакета. Исполняемый код — окончательный источник
истины; всё, что ещё не сделано, здесь помечено как план.

## Как продолжить работу

- Пакеты лежат в общем вендоре: `C:\SkeekS\dev\php\vendor\skeeks\cms-communication`
  и `...\cms-communication-imap`; репозитории `github.com/skeeks-cms/cms-communication`
  и `github.com/skeeks-cms/cms-communication-imap`. Перед правкой — умение
  `skeeks-cms-package-development`.
- Это доработка вендора для всех сайтов, а не кода skeeks.com.
- Пакеты выпущены на Packagist (`skeeks/cms-communication`,
  `skeeks/cms-communication-imap` 1.0.0) и стоят в боевых `composer.json` и
  `composer.lock` skeeks.com. Доработки сначала делаются в общем вендоре и
  проверяются на стенде (раздел «Стенд»), затем выпускаются новой версией.
- Раздел «Состояние работ» говорит, что уже сделано, что не закоммичено и что
  дальше. После каждого заметного шага обновлять его.

## Цель

Полная картина взаимодействия с клиентом в CRM: кто, что, когда отправил,
кто позвонил, в какой последовательности, человек или ИИ. Менеджер не уходит
в другие сервисы: звонит из карточки лида, оттуда же пишет письмо или
отправляет КП и видит ответ в ленте. Почта, боты (Telegram, MAX, ВК и др.),
СМС и звонки сходятся в одну ленту лида, компании, клиента, сделки.

## Главные принципы

1. **Одна операция — один сервис.** Ответить, создать задачу из сообщения,
   привязать к компании — одна серверная операция. Её вызывают интерфейс,
   инструменты `cms-mcp`, сценарии бота и ИИ. Логика не дублируется в
   контроллерах.
2. **ИИ — такой же исполнитель, как менеджер**: отдельный пользователь
   «ИИ-помощник» со своей ролью и правами, действует через те же операции,
   всё записано от его имени.
3. **У каждого действия есть исполнитель**: сотрудник, ИИ, система (правило,
   расписание) или внешняя сторона. Изменения только через сервисы, не прямым
   SQL — иначе журнал их не увидит.
4. **Сообщение хранится один раз**, в ленту записи попадает ссылка
   (`cms_log` типа `message`), как у звонков.
5. **Пакет необязательный.** Ядро `cms` от него не зависит; сайты без CRM его
   не ставят. Драйверы каналов — отдельные пакеты.
6. **Всё внешнее — через `cms-job`**: свои полосы, блокировки по подключению,
   без своих очередей. Неизвестный исход отправки не повторяется.

## Пакеты

| Пакет | Что в нём |
|---|---|
| `skeeks/cms` | Только точки расширения: отрисовка своих типов записей ленты (`Skeeks::$logRenderers`), типы ленты карточек (`Skeeks::$activityLogTypes`, `CmsLogQuery::activity()`, в том числе лента задачи), кнопки у телефона и email в карточках (`CrmContactBlockWidget::contactActions()` + событие), источники лида `email`, `max`, «создание из источника» (`Skeeks::$recordSources`, `source\RecordSources`, `?source=<тип>:<id>` в стандартном окне создания) |
| `skeeks/cms-backend` | Общие иконки почты в `BackendIcon` (inbox, send, reply, forward, mail-open, paperclip); исправлена зависимость скриптов ссылки на запись (`AjaxControllerActionsWidgetAsset` → `ControllerActionsWidgetAsset`) |
| `skeeks/cms-communication` | Подключения, ящики, права, переписки, сообщения, связи, лента, раздел «Почта», окно «Написать», фоновые задачи. Позже: уведомления клиентам, рассылки, сценарии ботов, шаблоны |
| `skeeks/cms-communication-imap` | Драйвер почты: свой клиент IMAP (без `ext-imap`), SMTP через `symfony/mailer`, подстановка серверов по домену и MX |
| Драйверы мессенджеров (план) | Telegram, MAX, ВК: приём событий, отправка, описание возможностей канала |
| Драйверы сервисов рассылок (план) | Unisender Go и аналоги: отправка через API, события доставки |
| `skeeks/cms-proposal` (этап 3) | Реестр КП: версии, позиции, шаблоны, PDF, страница КП по личной ссылке с учётом просмотров, «Принять» и «Задать вопрос»; зависит от `cms` и `cms-communication`, `cms-shop` — по желанию |
| `skeeks/cms-ai` (план) | Языковые модели, правила самостоятельности, журнал решений |
| `cms-mcp` (план) | Инструменты `cms_comm_*` для внешних клиентов и ИИ |
| `cms-mobile` | Push как ещё один канал уведомлений клиентам (план) |

`cms-shop`, `cms-hosting` и другие пакеты не зависят жёстко от коммуникаций:
публикуют события и регистрируют пункты меню бота, если пакет установлен;
без него всё работает как раньше (`cms-mailer`).

## Будущий реестр файлов хранилища: почта — первый кандидат

План общего реестра использования файлов хранилища ведётся в `skeeks/cms`
(`AGENTS.md`, раздел «Planned: storage file usage registry»; согласован
21.10.2026, не начат). Почта — первый кандидат на подключение: её реестр
`cms_comm_message_file` станет поставщиком сведений «файл используется в
письмах …», остальная почта не меняется. До появления реестра почта
соблюдает два правила:
- файл письма передаётся в другой раздел копией, а не ссылкой на тот же файл
  хранилища («Создать задачу из письма» и подобное);
- уборка файлов почты (срок хранения, кэш экономного режима) удаляет файл
  хранилища, только когда на него не ссылается ни один файл письма, а после
  появления реестра — и только если общая проверка «используется ли файл»
  отвечает «нет».

## Почта: решения

**Ящик и подключение.** Для пользователя одна форма «Почтовый ящик»: адрес,
имя отправителя, логин (по умолчанию адрес), пароль приложения, серверы
(подставляются сами для Яндекса, Mail.ru, Gmail, Rambler, Outlook и доменов на
их почте по MX). В модели подключение (логин) и ящик (адрес с правами)
разделены: несколько адресов могут приходить в один логин (алиасы, пересылка
в папки) — в форме «Письма приходят в другой ящик». Отдельный раздел
подключений из меню убран.

**Пароли** хранятся зашифрованными в БД ключом из protected params
(`params['cms-communication']['secretKey']` или `CMS_COMMUNICATION_SECRET_KEY`),
в форме не показываются, пустое поле оставляет прежний. Это зафиксированное
исключение из правила о секретах (умение, `external-service-secrets.md`).

**Права сотрудника на ящик** (владельца нет, прав у каждого свой набор):
чтение — всё / только связанное / нет; отправка — любой адрес / только своим /
нет; управление ящиком; управление письмами на сервере; «по умолчанию»;
«ответственный» (служебные уведомления). Пример: info@ — Светлана и Александр
читают всё и пишут; новый менеджер — «связанное» + «своим» и info@ по
умолчанию: видит и пишет только своим лидам.

**Раздел «Почта»** открыт каждому сотруднику с доступом в админку
(`permissionNames` — только общее право «Доступ к системе
администрирования» `CmsManager::PERMISSION_ADMIN_ACCESS` в
`AdminCmsCommMessageController` и `AdminCmsCommTemplateController`; не
`permissionName = null` — тогда право раздела создаётся только для
администраторов; и не пустой список — тогда права не проверяются вовсе и
гость получает ошибку вместо страницы входа, исправлено в 1.1.1). **Видимость письма**: чтение «всё» на его ящик,
или он отправил письмо, или письмо привязано к лиду/компании/клиенту, которых
он видит по `forManager()` (если у ящика включено «показывать через связанные»;
для личных ящиков можно выключить). Отправка «только своим» проверяется на
сервере.

**Администратор в почте — по общим правилам** (решение владельца
23.10.2026): что он читает, с каких ящиков пишет и какими письмами
управляет, задают его собственные строки доступа к ящикам, а не роль
(`forManager()`, `MailFolders::accounts()`, `MailComposeService`,
`MailboxActions`, `MessageSorting`). За ролью остаются настройка ящиков и
подключений, права сотрудников, «Настройки почты», «Сбор писем», очистка и
сохранение файлов, общие шаблоны ящиков. Чтобы видеть ящик целиком,
администратор выдаёт себе доступ, как любому сотруднику.

**Скрыто по умолчанию** (решение владельца 23.10.2026, интерфейс
перегружен): «Ответственный» за переписку — меню в письме, строка в шапке,
«Назначить меня» в меню строки, папка «Мне назначено», фильтр и метка в
строке (письмо, требующее работы, становится задачей); фильтр «Привязка» —
его заменяют папки «Мои клиенты» и «Без привязки». Данные и операции
остались; сайт включает их `communication.showAssignee` и
`communication.showLinkedFilter`. Фильтр, уже стоящий в адресе списка,
показывается, чтобы его можно было снять.

**Приём**: «Входящие» + «Отправленные» (по отметке `\Sent` или названию),
30 дней при первом приёме, дальше по UID. Одно письмо в нескольких ящиках —
одно сообщение. Письма, отправленные из Яндекса, Outlook, с телефона,
забираются из «Отправленных». Расписание — раз в 2 минуты; кнопка «Проверить
новые письма».

**Сбор писем** (карточка ящика → «Сбор писем», только администратор): письма
«Входящих» и «Отправленных» за 3 месяца … 3 года, все или с даты — задача
`comm.mail.history` (`MailHistoryJobHandler`), только чтение. Каждое письмо
принимается обычным `MailIngestService::ingest(..., history: true)`: привязка
к лидам, компаниям, клиентам и лента по дате письма, но `is_history = 1` —
считается прочитанным (не входит в счётчики, без «Не прочитано»; будущие
уведомления о новых письмах такие письма пропускают). Граница папки — курсор
обычного приёма (`cms_comm_sync_state.last_uid`), у ни разу не принимавшейся
папки — начало окна `initialDays`: новые письма остаются приёму и приходят
непрочитанными. Уже известные письма пропускаются по месту на сервере без
загрузки, затем по Message-ID, поэтому повторный или более широкий сбор ничего
не задваивает. Задача идёт порциями по 2 минуты: курсор (папка, UIDVALIDITY,
последний UID, граница) сохраняется с прогрессом, между порциями блокировка
ящика `comm-connection:N` свободна, и обычный приём проходит. Файлы писем
старше `keepDays` при приёме не сохраняются в CRM (догружаются из ящика при
открытии) — иначе их сохранила бы и на следующий день удалила уборка.

**Привязка**: точное совпадение адреса с email активного лида, компании,
клиента (не сотрудника); ответ с другого адреса — по цепочке. «Наши» адреса —
ящики, сотрудники и любые адреса на доменах наших ящиков (кроме общих
сервисов: gmail.com, yandex.ru и т. п.); письма, где все участники наши,
считаются внутренними и не привязываются.

**Отправка**: письмо `queued` и задача в одной транзакции, Message-ID задаём
заранее; SMTP ящика; затем копия в «Отправленные». Яндекс сам SMTP-письма в
«Отправленные» не кладёт и не умеет искать по заголовку — проверяем последние
письма папки. Через личный SMTP массово не слать.

**Показ письма**: HTML со своими стилями во фрейме без скриптов и форм;
вырезаются скрипты, фреймы, формы, обработчики, `javascript:`. Внешние
картинки, фоны и `url()` скрыты до «Показать картинки» (иначе отправитель
узнаёт об открытии, срабатывают служебные ссылки, а зависшая картинка-счётчик
держала панель 30 секунд). Письмо вставляется после открытия панели.

**Интерфейс «Почта»** (главное меню): слева «Написать», «Проверить новые
письма», папки «Все письма», «Мои клиенты», «Без привязки» и ящики с чтением
«всё» («Входящие», «Отправленные»), у папок счётчики непрочитанных. «Мои
клиенты» — письма, привязанные к лидам, компаниям и клиентам, которые
сотрудник видит в CRM (`linkedToVisible()`), а не любые привязанные письма
читаемого ящика; метки CRM в списке и в письме тоже только видимые ему
(`MailUi::visibleLinks()`): ссылка на карточку без доступа запускала бы её
единственное действие «Удалить». Список как
в Яндекс Почте: флажок, кружок с инициалами, отправитель, точка «не прочитано»,
тема + начало текста, метки CRM, скрепка, дата; выбор писем, «Прочитано»/«Не
прочитано». Письмо — в стандартной панели справа: «Ответить», «Переслать», «Не
прочитано», отправитель, «Кому», справа записи CRM (логотип, открывают
карточку записи). Свои CSS/JS на переменных темы, иконки — `BackendIcon`
(недостающие «ответить всем» и «картинка» пока нарисованы в `MailUi` тем же
стилем; перенос в `BackendIcon` — только по согласованию, это общий слой).

Устройство экрана: прокручивается страница, а не список; папки и шапка списка
— `position: sticky` под шапкой админки (`--sx-shell-top-offset`). Общая
обёртка `.sx-main-wrapper` в `cms-backend` режет переполнение `overflow:
hidden`, что ломает sticky, поэтому только на странице почты стоит
`.sx-main-wrapper:has(.sx-mail) { overflow: clip }` в `mail.css`. Если такое
понадобится другим разделам — менять общую оболочку по согласованию.
Порции списка: `mail?portion=2&before=<дата>&before_id=<id>` отдаёт JSON со
строками (`_rows.php`). Открытое письмо одно: следующее заменяет панель.

**Форма письма** (`create`): GET — форма (`?inline=1` — только форма для
вставки под письмом), POST — JSON `{success, id}` или `{errors}`. Параметры:
`to`, `context_model_code/_id`, `reply_to` (+`all=1` — ответ всем, без наших
ящиков), `forward`. Редактор текста — общий лёгкий виджет `skeeks/cms`
`RichTextInputWidget` (решение владельца 21.10.2026: CKEditor 4.4.7 из
`yii2-ckeditor` устарел; редактор, сделанный для почты, вынесен в общий и
используется в задачах, разделах, комментариях). Набор возможностей письма —
`ComposeForm::EDITOR_PRESET` (standard + выбор шрифта: шрифт выбирается
только в письмах) и `EDITOR_TOOLS` (без заголовков); абзац — `div`. Текст
чистится той же настройкой (`RichTextHtml::clean`), текстовая часть
строится из HTML (`RichTextHtml::toText`). Файлы, брошенные на зону
«Прикрепить файлом» редактора, приходят в почту событием `sx-rte:attach`;
брошенные на остальную форму — прикрепляются как раньше. Цитата
(`include_quote`) и пересылаемое письмо не входят в текст формы — их
добавляет `MailComposeService::queue()`. Скрытая копия хранится в
`bcc_list` и видна только у нас. Подсказки адресатов (`contacts?q=`) — только
то, что сотрудник и так видит (`forManager()`), работают в веб-запросе.

**Файлы писем** (`services\MailFiles`, таблица `cms_comm_message_file`:
письмо → файл хранилища, имя, `content_id`, `is_inline`). Байты — в хранилище
CMS (`Yii::$app->storage->upload()`; в очереди `cms_site_id` задаётся явно).
Файлы, загруженные в форму (вложения, перетаскивание, вставка скриншота),
ждут во временной папке CMS (`ajaxfileupload` `private_tmp_dir`,
`MailFiles::storeTemp()` поверх общего `skeeks\cms\services\TemporaryUploads`
с префиксом `mail`; токен привязан к сессии сотрудника) и переезжают в
хранилище только при отправке письма (`storeFromTemp()`). Закрытое письмо,
убранное вложение или картинка не оставляют ничего в хранилище: временную
папку раз в сутки чистит стандартный агент `ajaxfileupload/cleanup` (файлы
старше часа). Решение владельца 21.10.2026 — так же делать во всех формах с
файлами (задачи, новости), правило в умении (`resumable-file-uploads.md`).
Ссылки хранилища в интерфейсе не показываются: всё идёт через `file?id=`
(проверка, что сотрудник видит письмо) или `file?t=` (свой временный файл
этой сессии). Прямо в странице показываются
только растровые картинки по типу, который определило хранилище, остальное —
скачивание с `nosniff`. Картинка в тексте при отправке становится частью
письма (`DataPart::asInline()->setContentId()`), в HTML — `src="cid:…"`; при
показе `MailHtml::sanitize()` подменяет `cid:` ссылками на файлы письма.
Редактор отдаёт картинки как `<img data-sx-upload="токен">` (загрузка — через
почтовое `upload` с правом отправки и пределом 25 МБ), очистка пропускает
только такие картинки и стили панели с проверкой значений.
Предел — 25 МБ на файл и на все вложения письма (`MailFiles::MAX_SIZE`);
больше — у входящих сохраняется только имя. Письмо не уходит, если файла нет
в хранилище. Скрытая копия проверяется настройкой `allowedRecipients`
наравне с «Кому» и «Копией».

Одинаковое содержимое хранится один раз на сайт: у файла письма есть
`content_hash` (SHA-256) и размер; при приёме (`MailFiles::storeReceived()`)
и при отправке своих загрузок (`storeFromTemp()`) сначала ищется уже
сохранённый файл с тем же отпечатком, и новое письмо ссылается на него
(логотипы подписей, повторные рассылки, один прайс в разных письмах). Поэтому
один файл хранилища может принадлежать многим письмам: удалять его можно,
только когда на него не ссылается ни один файл письма (удаление писем и
черновиков обязано это проверять). Удаление записи хранилища теперь не
убирает файл из писем (связь `SET NULL`): файл остаётся описанным и
подгружается из ящика.

**Хранение файлов настройками.** Общие настройки — компонент
`components\MailFileSettings` на уровне сайта (по правилам
`component-settings.md`: на основном сайте запись по умолчанию), страница
«Настройки почты» → «Хранение файлов» (`AdminCmsCommSettingsController`,
только администратор). У ящика — `cms_comm_account.file_settings` (JSON,
null — как в общих), блок «Хранение файлов» в его карточке. Действующие
правила — `services\MailFilePolicy`: по умолчанию «Минимальный» (22.10.2026);
режим «Полный» (всё у себя),
«Экономный» (картинки у себя, вложения из ящика), «Минимальный» (всё из
ящика), «Выборочно»; порог размера; `keepDays` — срок копий по дате
письма (по умолчанию 365 дней, удаляет ежедневная уборка; 0 — всегда); `cacheDays` — срок копии, подгруженной по запросу,
после последнего открытия. Письмо в нескольких ящиках следует самому
«хранящему» из них. Текст письма хранится всегда. Форма показывает только
нужное режиму: порог и `keepDays` — когда что-то хранится, `cacheDays` —
когда что-то берётся из ящика (его нет у «Полного» и «Выборочно» со всеми
отметками без порога размера). Форма настроек сайта имеет свой id
(`sx-mail-file-settings`): форма таймера работы в шапке тоже `w0`, и
динамическая перезагрузка поля по `#w0` отправила бы таймер.

**Файл без копии в CRM** — строка `cms_comm_message_file` с
`storage_file_id = null`, номером файла в письме `part_index`, размером и
отпечатком. При приёме строка создаётся всегда, байты сохраняются, только
если правила ящика это разрешают (уже сохранённое одинаковое содержимое
переиспользуется в любом режиме). Подгрузка — задача
`comm.mail.fetch-files` (`MailFileFetcher`, через `cms-job`, не в
веб-запросе): письмо читается заново только для чтения по папке и UID копии
(`cms_comm_message_mailbox`), при другой UIDVALIDITY считается
недоступным; файл находится по `part_index` с проверкой имени и размера,
затем по Content-ID. Если правила ящика такой файл хранят (письмо, принятое
до сохранения файлов, в «Полном» режиме), копия остаётся навсегда; иначе
помечается `is_cached` и `last_access_at` и уходит через `cacheDays`. Экран
письма сам запрашивает картинки текста, вложение — по нажатию, затем
скачивание; страница опрашивает `fetch-status` (готовность файлов и
`pending` — идёт ли задача). У писем, полученных до сохранения вложений,
первая подгрузка описывает все их файлы. Пересылка и цитата сначала
подгружают недостающие файлы исходного письма. Отправленное из CRM письмо
получает место на сервере, когда приём находит его в «Отправленных»
(`addCopy` дописывает папку и UID).

**Сохранить файлы в CRM** («Настройки почты», только администратор) —
обратное очистке: ящик, срок писем (как в «Сборе писем»), картинки и/или
вложения, порог размера; «Посчитать» (`MailFileSave::preview`: сколько
загрузить и их размер по `size` строк, сколько временных копий станет
постоянными), затем задача `comm.mail.save-files`
(`MailSaveFilesJobHandler`). Задача идёт по письмам по возрастанию id:
временная копия только перестаёт быть временной, недостающие файлы
загружаются `MailFileFetcher` (`onlyIds`, `keepForGood`) — одно чтение письма
на все его файлы, одна IMAP-сессия на подключение на всю порцию; порции по
2 минуты с курсором. Блокировку ящика не берёт (только чтение), приём идёт
рядом. Срок `keepDays` действует и на сохранённое: страница предупреждает, если
выбранные письма старше него. Проверено на стенде: после ручной очистки 65
файлов задача вернула их все (и 4 временные сделала постоянными), отпечатки
совпали.

**Очистка** — задача `comm.mail.cleanup-files` (`MailFileCleanup`):
ежедневно по агенту (`auto` — `keepDays` и `cacheDays` каждого ящика) и
вручную администратором («Очистка файлов»: старше N дней, вложения и/или
картинки, больше N МБ, ящик; сначала «Посчитать», затем запуск со ссылкой на
ход выполнения). Удаляется только копия в CRM (`MailFiles::forget()`; сам
файл хранилища — когда на него не ссылается ни одно письмо), строка письма
остаётся. Никогда не удаляется копия письма без известного места на сервере
(отправленное, ещё не найденное в «Отправленных», или удалённое из всех
ящиков): там копия в CRM единственная.

**Подписи и шаблоны** (`services\MailTemplates`, 22.10.2026). «Мои
настройки почты» (`admin-cms-comm-message/personal`, ссылка под папками
«Почты» и пункт меню «Шаблоны» в форме письма): уведомления по ящикам,
подпись для каждого ящика с правом отправки (общий `RichTextInputWidget`),
список шаблонов. Подпись подставляется в новое письмо, ответ, пересылку и
быструю строку ответа блоком `data-sx-mail-signature` под пустой строкой,
то есть над цитатой (цитату добавляет сервер при отправке); смена «От
кого» заменяет блок подписью другого ящика или убирает его. Черновик подпись
не подставляет повторно (атрибут блока сервер вычищает, после повторного
открытия подпись — обычный текст). Шаблон — личный (виден только автору, в
любом ящике) или общий для ящика (всем, кто пишет с него; добавлять и
менять — тем, у кого «Управление ящиком», и администраторам); добавляются и
меняются в стандартных окнах `AdminCmsCommTemplateController` (открывается
только то, что сотрудник может менять; выбор «Кому доступен» — виртуальное
поле `scope`, так как select2 теряет подпись пустого значения). Вставка — в
место курсора, иначе в начало текста над подписью. Подписи и шаблоны чистятся
`MailTemplates::EDITOR_PRESET` — форматирование письма без картинок:
временные загрузки истекли бы в сохранённом тексте (картинки в подписях —
план).

**Черновики** (`services\MailDrafts`, 22.10.2026). Форма письма сохраняет
себя через 2 секунды после изменения (`draft`, только один запрос за раз,
повтор после него) и при закрытии окна (`sendBeacon`); пустое заполнение
формы (адресат ответа, подпись) черновиком не считается. Адресаты хранятся
как набраны, письмо проверяется только при отправке; сохраняются только
свой ящик, видимые письма и записи CRM. Черновик ответа помнит письмо
(`reply_to_message_id`, «Ответить всем»): «Ответить» на этом письме
продолжает его, строка ответа пишет «Продолжить черновик ответа». Файлы:
форма работает с временными загрузками сессии; при сохранении каждая новая
загрузка копируется в хранилище (`cms_comm_draft_file`, одинаковое
содержимое писем и черновиков переиспользуется, временный файл остаётся у
открытой формы), при открытии черновика в другой сессии байты снова кладутся
во временную папку под новым токеном, текст черновика сразу получает новые
токены. Отправка удаляет черновик (файлы, взятые письмом, остаются у
письма), «Удалить черновик», крестик в папке и «Отменить» под письмом —
тоже. Файл хранилища удаляется, только когда на него не ссылается ни письмо,
ни черновик (`MailFiles::deleteUnused()`, им пользуется и уборка файлов
писем). Ежедневная уборка `comm.mail.cleanup-files` (`auto`) удаляет
черновики, которые не меняли «Хранить неотправленные черновики, дней»
(«Настройки почты» → «Хранение файлов», по умолчанию 90, 0 — не удалять).

## Уведомления

- Сотрудникам — только `CmsWebNotify` (стандартный колокольчик CRM, своей
  таблицы нет). **Сделано 22.10.2026** (`services\MailNotifier`):
  - кому: сотрудникам со строкой прав на ящик письма, у которых чтение «все
    письма» или «только связанные» и письмо им видно
    (`CmsCommMessageQuery::forManager()`), сотрудник активен и не выключил
    «Уведомлять о новых письмах» для этого ящика
    (`cms_comm_account_access.is_notify`, «Мои настройки почты»).
    Администратор без строки прав не уведомляется: видеть все ящики — не
    просьба получать каждое письмо;
  - о чём: только новые входящие письма обычного приёма
    (`MailPollJobHandler` собирает созданные за запуск письма и вызывает
    `notifyNew()` после приёма, ошибка уведомлений не отменяет приём). Не
    уведомляют: «Сбор писем» (`is_history`), первый приём папки (окно
    `initialDays`), повторный просмотр папки после смены UIDVALIDITY,
    исходящие, «Отправленные», письма, которые сотрудник уже прочитал;
  - несколько писем одного запуска — одно уведомление сотруднику («3 новых
    письма, последнее от …»);
  - уведомление ссылается на (последнее) письмо как на запись:
    `model_code` = класс `CmsCommMessage`, `model_id`; письмо
    зарегистрировано в `skeeks->modelsConfig` (в `CommunicationBootstrap`,
    не в конфиге: конфиг заменил бы весь список ядра), поэтому колокольчик
    сам строит ссылку и открывает письмо «Почты» в панели. URL не хранится:
    задача приёма работает в консоли, где префикс админки проекта (`~sxx`)
    неизвестен. Открытие письма отмечает его уведомление прочитанным;
  - видимость «только связанных» в консоли: связи ядра
    (`CmsCompany::getManagers()`, `User::getSubordinates()` и др.) берут
    класс пользователя из компонента `user`, которого в консоли нет, —
    `MailNotifier::withUserComponent()` ставит его без сессии на время
    проверки.
- Назначение ответственным за переписку уведомляет назначенного (сделано
  23.10.2026, `MessageSorting::assign()`). План: уведомлять ответственного о
  новых письмах его переписки, исполнителя лида и менеджеров компании без
  прав на ящик; выбор «только от клиентов».
- Клиентам — пакеты регистрируют виды событий (счёт выставлен, не оплачен N
  дней, услуга заканчивается, задача выполнена) с шаблонами по каналам.
  Каналы клиента: email, СМС, push (`cms-mobile`), подтверждённые боты.
  Правила: во все, по приоритету, с запасным каналом (при ошибке доставки),
  обязательный + удобный (счета: email всегда), как выбрал клиент. Стабильный
  ключ события исключает повтор. В ленте одна запись со статусами каналов.
  Тихие часы, лимит частоты, отписка только от информационных. Получатели
  компании — контакты с `is_notify`.

## Мессенджеры и боты

- Подключение бота — тот же `cms_comm_connection` с драйвером; карточка бота:
  настройки, доступ сотрудников, собеседники, чаты и каналы, переписки, журнал.
- Переписка — общее понятие: личная, групповой чат, канал, цепочка писем.
  Наши сотрудники в группе — тоже собеседники («от нас»). Состав и права бота
  в чатах — по событиям мессенджера (в Telegram для чтения группы нужен
  отключённый режим приватности или права администратора; MAX сверить).
- Связь переписки с любой записью (компания, сделка, проект) через
  `cms_comm_link`; для шумных групп в ленте — только отмеченные сообщения или
  сводка за день.
- Бот как мини-кабинет: меню из пунктов, которые регистрируют пакеты
  («Мои заказы», «Счета», «Мои услуги»); ответ не привязан к мессенджеру —
  драйвер рисует кнопки по своим возможностям. Вход: ссылка из кабинета
  (`t.me/bot?start=<ключ>`), «Поделиться номером», код из СМС через
  существующий вход по коду. Данные — только подтверждённому клиенту, по
  правилам кабинета клиента; в группах личного не показываем. Сложные экраны —
  кабинет клиента как мини-приложение. Привязка видна в карточке клиента
  («Мессенджеры»), её можно отвязать.
- Свободный текст — в диалог с менеджером («взять диалог»), команды и кнопки —
  в сценарий.

## Действия в ящике и сверка с сервером

Сделано 23.10.2026 (этап 2, пункт 1). Одна операция на действие —
`services\MailboxActions` (для «Почты», будущих правил и `cms-mcp`), работа
с сервером — `services\MailServerSync` внутри задач подключения.

- **Право** — «Управление письмами» (`cms_comm_account_access.can_manage_messages`)
  на ящик копии письма; администратор может всё. Без права кнопок нет
  (`canManageAny()`, `canManage($message)`), сервер отвечает 403 или
  пропускает письмо с причиной. Метки меняют те же сотрудники.
- **Перенос — просьба, потом сервер.** `move($messages, $action, $folder)`
  (trash, archive, junk, restore — во «Входящие» или «Отправленные» по
  направлению, folder — папка ящика) записывает у копии `target_role`
  (+ `target_folder`), пересчитывает `box_state` и ставит задачу
  `comm.mail.apply` подключения. Экран сразу показывает письмо на новом
  месте: место для сотрудника — `COALESCE(target_role, folder_role)`
  (`CmsCommMessageMailbox::roleExpression()`). Просьба вернуть туда, где
  письмо лежит на сервере, отменяет невыполненный перенос. Копии других
  ящиков того же подключения с тем же местом (алиасы) переносятся вместе.
  Письмо без места на сервере (отправлено из CRM и ещё не найдено в
  «Отправленных», удалено в почте) не переносится — с причиной.
- **Задача `comm.mail.apply`** (`MailApplyJobHandler`, полоса
  `communication`, `resourceKey` `comm-connection:N` как у приёма,
  наложение `coalesce`: при работающей задаче ставится одна ожидающая)
  читает просьбы в момент запуска, группирует по исходной папке и цели,
  проверяет UIDVALIDITY, переносит `UID MOVE` (без MOVE — `UID COPY`,
  `STORE \Deleted`, `UID EXPUNGE`), новый UID берёт из `COPYUID`, без него —
  по Message-ID среди новых писем папки. Удачно — у копии новые папка, UID и
  роль; письма нет в исходной папке или сервер отказал — просьба снимается,
  у копии `sync_error`, сотруднику, который просил, — `CmsWebNotify`; письмо
  остаётся там, где оно на сервере. Приём почты делает то же в начале
  своей сверки (страховка). Драйвер без `MailManageSessionInterface` —
  просьбы снимаются с причиной.
- **Папки сервера.** `MailManageSessionInterface::folderList()`: роли по
  SPECIAL-USE (`\Trash`, `\Junk`/`\Spam`, `\Archive`, `\Sent`, `\Drafts`;
  `\Templates` — тоже черновики), без отметок — по известным именам папок
  верхнего уровня (или детей INBOX). У Яндекса нет папки архива — её, как и
  сам Яндекс, создаёт первое архивирование («Архив»). Каждая папка, кроме
  «Входящих» и «Отправленных», получает строку наблюдения в
  `cms_comm_sync_state` (роль, разделитель, `last_uid` — до какого UID
  просмотрена); эти строки — список «В папку» (входящие, архив, обычные
  папки), без обращения к серверу из веб-запроса.
- **Сверка при приёме** (`MailServerSync::reconcile()`, после приёма новых
  писем): для каждой папки, где есть копии, `UID SEARCH UID <известные>`;
  копии, которых нет, ищутся по Message-ID среди писем, появившихся в
  наблюдаемых папках после `last_uid` (при первом взгляде — за срок самого
  старого пропавшего письма, не больше 2000). Нашлось — копия переезжает;
  нет — `gone` (удалено в почте), письмо уходит из обычных папок в
  «Корзину» CRM с пометкой «Удалено в почтовом ящике». Письмо, вернувшееся
  во «Входящие» или «Отправленные», принимается заново по Message-ID, и
  копия занимает новое место (`MailIngestService::addCopy()`), поэтому
  письма не задваиваются; копия в другой папке приёма (письмо себе) остаётся.
  Проверено на стенде: письмо, перенесённое в Яндексе в «Спам», а затем
  обратно, в CRM прошло тот же путь, число писем не изменилось.
- **Папки «Почты».** У каждого ящика с чтением «всё» — «Входящие»,
  «Отправленные» (без перенесённых в архив и папки), «Архив», «Спам»,
  «Корзина» (счётчик не показывается). «Все письма», «Мне назначено», «Мои
  клиенты», «Без привязки» не показывают письма с `box_state`. В списке у
  письма — метки, папка ящика, «Переносится: …», «Не перенесено» (подсказка —
  причина); в шапке письма — то же и текст ошибки.
- **Выбрать все письма папки.** Когда отмечены все показанные строки, а в
  папке их больше, панель выбора предлагает «Выбрать все письма папки: N»;
  действие уходит с `all=1` и фильтрами списка (папка, поиск,
  непрочитанные, ответственный, привязка, метка), сервер строит тот же
  запрос (`listQuery()`), не больше 5000 писем за раз.
- **Метки** — данные CRM (`cms_comm_label`, общие для сайта, цвет из
  палитры), фильтр «Метка» в списке. Где папка хранит свои ключевые слова
  (`PERMANENTFLAGS` содержит `\*`; Яндекс — да), задача пишет их как флаги
  `SkeekS_label_<id>` и снимает снятые (`labels_dirty`); с сервера метки не
  читаются. «Это спам» / «Не спам» дополнительно ставят `$Junk` /
  `$NotJunk`, где сервер это позволяет.

## Поиск по переписке

Поиск «Почты» находит переписку, в любом письме которой есть каждое слово
запроса (слова короче двух букв пропускаются, не больше пяти): отправитель,
получатели, тема и текст, у писем без текстовой части — текст из HTML
(раньше такие письма, 1119 из 1686 на стенде, не находились). Строка
поиска письма — `cms_comm_message_search` (нижний регистр, «ё» как «е»,
до 20 000 знаков текста, `utf8mb4_bin`), её пишет
`CmsCommMessage::afterSave()` для любого писателя. Запрос —
`cms_comm_conversation_id IN (переписки со словом)`; совпадения считаются
только в письмах, которые сотрудник может читать (администратору — без
проверки). План на стенде (1689 писем, 6 МБ строк поиска): подзапрос
материализуется по узкой таблице, ~30 мс; прямой перебор текстов и HTML
писем — ~190 мс. На десятках тысяч писем следующий шаг — FULLTEXT по той же
таблице.

## Спам и правила разбора

Согласовано с владельцем 23.10.2026, реализация отложена (этап 2, пункт 4).
Спама много, поэтому автоматика не должна превращать его в записи CRM.

- **Лиды из писем незнакомых отправителей автоматически не создаются.** Такие
  письма лежат в «Неразобранных», лид создаётся одним щелчком (этап 2, пункт 3).
  Иначе CRM заполняется мусором.
- **Первый фильтр — почтовый сервис.** Забираем только «Входящие» и
  «Отправленные», папку «Спам» не забираем. «Это спам» в CRM переносит
  письмо в папку спама на сервере, чтобы фильтр сервиса учился.
- **Рассылки и автоматические письма не порождают записей**: заголовки
  `List-Unsubscribe`, `Precedence: bulk/list/junk`, `Auto-Submitted` (кроме
  `no`), отправители `noreply@`/`mailer-daemon@`, домен или адрес из
  стоп-списка CRM (пополняется кнопкой «Это спам»).
- **Автоматика только при сильном сигнале**: письмо от известного клиента
  (адрес есть в CRM) может стать задачей; автоответ «задача №… принята»
  уходит только известным адресам, не на автоматические письма и не чаще раза
  в сутки на переписку. Автоответ незнакомым запрещён: он подтверждает
  спамерам живой адрес и при подделанном отправителе уходит постороннему.
- **«Лид из каждого письма»** — только настройкой отдельного ящика заявок
  (zakaz@, письма форм сайта), по умолчанию выключено.
- **ИИ (этап 8)** помечает письмо «похоже на заявку» и предлагает лид, но
  сам его не создаёт.

## Действия над сообщением

Меню у любого сообщения (письмо, бот, чат): «Создать задачу / лид / сделку»,
«Привязать», «Ответить», «Переслать». Форма создания открывается заполненной
(тема, цитата, вложения, связи переписки), после сохранения — связь «создано
из сообщения» и отметка у сообщения. Статусы задачи и ответы менеджера могут
уходить обратно в переписку («Задача №124 принята / выполнена»). В ядре для
этого — «создание из источника» (`source=model_code:id`), полезное и для
«задача из звонка», «сделка из лида».

**Сделано для писем (23.10.2026).** Ядро (`skeeks/cms`): реестр
`Skeeks::$recordSources` (тип → `source\RecordSourceInterface`: `find`,
`supports`, `prefill`, `enforce`, `created`, `describe`) и обработчики
стандартного окна создания `source\RecordSources`: окно любой модели с
`?source=<тип>:<id>` заполняется источником, над полями — строка «Из письма
«…» от …», после сохранения источник связывает запись в той же транзакции.
Почта регистрирует тип `message` (`source\MessageRecordSource`), вся работа —
в сервисе `services\MessageRecordFactory` (на него обопрутся правила части 4
и инструменты `cms-mcp`: `create($message, $type, $attributes)` создаёт и
сохраняет запись без окна):
- задача: название — тема, описание — «Письмо от …, дата» и собственный
  текст письма без цитат (`helpers\MailText`: блоки цитат почтовых программ,
  строки «> », вводные строки «…пишет:», «On … wrote:»), лид, компания или
  клиент письма, видимые сотруднику (компания или клиент лида, если у письма
  своих нет);
- лид: название «Письмо «тема»: имя, адрес», описание, источник `email`,
  название источника — наш ящик, `source_data` (id письма, Message-ID, от
  кого, тема), компания и клиент письма; после сохранения — адрес
  отправителя в email лида (если он не наш). `source_ref` не заполняется:
  какой лид создан из письма, знает связь `created`;
- сделка: название — тема, компания или клиент письма; описание сделки
  видят клиенты, поэтому текст письма в неё не попадает.
После сохранения письмо получает связь `created` с записью (отметка
«Задача №…», «Лид №…», «Сделка №…» в шапке письма и в строке списка), а
остальные письма переписки — `thread`; в ленте записи («Создано из входящего
письма») видны все письма переписки. Вверху карточки задачи, лида и сделки —
заметная строка «Создано из письма «Тема» от …, дата», тема открывает письмо
в панели (ядро: `source\RecordOriginInterface` + `RecordOriginWidget`, почта:
`MessageRecordSource::origins()`; сотруднику без доступа к письму — «из
почтового ящика, к которому у вас нет доступа», без ссылки). С 23.10.2026
(выпуск 1.2.1) там же для любой привязанной к письмам задачи,
лида или сделки — «Письмо «Тема» от …» или «Переписка последнее из N: …»
(видимые сотруднику письма, кроме того, из которого запись создана; тема
открывает письмо). Лента задачи показывает типы
`Skeeks::$activityLogTypes` (в ядре заменено `comments()` на `activity()`).
Файлы письма в запись пока не переносятся (по правилу «файл — копией», см.
реестр файлов).

## Разбор писем

`services\MessageSorting` (23.10.2026) — ручной разбор, одна операция на
действие для «Почты», будущих правил и `cms-mcp`:
- `link($message, $type, $id, $conversation)` — письмо или вся переписка к
  лиду, компании, клиенту или сделке, которую сотрудник видит
  (`services\CrmRecords::find()` — те же `forManager()`); пишет
  `MessageLinker` с типом `manual`, лента — как у автоматической привязки;
  снимает исключение;
- `unlink(...)` — удаляет связи и их записи в ленте; для всей переписки
  запоминает исключение (`cms_comm_link_exclusion`);
- `assign($message, $userId|null)` — ответственный за переписку: только
  активный сотрудник, которому письмо видно (`forManager($user)`),
  назначенному (не себе) — `CmsWebNotify` «Вас назначили ответственным за
  переписку «…»» со ссылкой на письмо (как уведомление о новом письме);
- `createdRecords()` — записи, созданные из письма, для отметок.
Видимость письма через привязку (`forManager()`, «Мои клиенты») теперь
учитывает и сделки, и задачи (`CrmRecords::types()`); для этого в ядре
`CmsTaskQuery`/`CmsDealQuery::forManager($user)` передают сотрудника во
вложенные условия. Метки CRM показываются только видимые сотруднику
(`CrmRecords::isVisible()`).

Интерфейс: в панели письма «Привязать» (окно `link`, клавиша l), «Создать ▾»
(только разрешённые сотруднику окна создания), «Ответственный ▾» (список
`assign` GET, выбор POST), строка «Ответственный: …», «×» у записи
(«Только это письмо» / «Всю переписку»); после действия письмо и список
обновляются сразу. В списке — меню строки (правая кнопка мыши или «⋮»):
открыть, прочитано/не прочитано, привязать, создать задачу/лид/сделку,
назначить меня; фильтры «Ответственный» (все, я, без ответственного,
другие ответственные видимых переписок) и «Привязка» (`assignee`, `linked`
в адресе списка и «Показать ещё»); папка «Мне назначено» (`assigned`).
С 23.10.2026 «Ответственный» и фильтр «Привязка» по умолчанию скрыты, см.
«Почта: решения».
Панель письма открывается с `updateSuccessCallback`: сохранённая из письма
запись помечает панель изменённой, и стандартная реакция при её закрытии
перезагрузила бы всю страницу — вместо этого обновляется только список.

## ИИ

ИИ — пользователь CRM со своей ролью, инструменты — те же `cms-mcp`. Уровни
самостоятельности для бота, переписки и вида действия: выключен,
подсказывает (черновик на подтверждение), действует и сообщает, полностью сам
(цены, сроки, деньги — никогда сам). Если менеджер взял диалог или ответил —
ИИ молчит. Сценарий группового чата: клиент пишет «поправить баннер» → разбор
переписки (с паузой, чтобы собрать сообщения) → проверка открытых задач
компании → задача → ответ в чат → по выполнении правило пишет в чат. Журнал
решений `cms_ai_run` с отметками «верно/неверно». Сообщения клиента — данные,
а не команды: права инструментов ограничены привязанной компанией и этой
перепиской; лимиты. Модель выбирается на уровне сайта (152-ФЗ: российская или
зарубежная). Пакет `cms-ai`.

## Рассылки и КП

- Рассылка создаёт обычные сообщения пачкой (`ChunkedJobHandler`), каждое в
  ленте своего лида; получатели фиксируются при запуске и только из видимых
  менеджеру; сводка исключённых и предпросмотр перед запуском; пауза, отмена,
  отчёт. Стоп-лист при любой отправке, ссылка «отписаться» и
  `List-Unsubscribe`, согласие для рекламы (38-ФЗ).
- Ящик рассылок (например promo@) — обычный ящик с правами, но отправка через
  API сервиса (Unisender Go и аналоги, транзакционная отправка с нашим id в
  метаданных и событиями доставки по вебхуку); приём ответов — IMAP или
  `Reply-To` на рабочий ящик. Домен настроить (SPF, DKIM), отключить пиксели и
  подмену ссылок для личных КП.
- «Открыто» по пикселю ненадёжно; надёжный сигнал — просмотр КП на нашей
  странице, см. «КП (реестр предложений)». Рассылка КП на 100 лидов — это
  100 отправок КП, у каждой своя ссылка.

**Схема рассылок** (согласовано с владельцем 23.10.2026, этап 4).

- **Кампания** — сущность `cms-communication`: аудитория (лиды или компании по
  фильтру либо импорт), содержание, канал, расписание, отчёт. Получатели
  фиксируются при запуске; каждая отправка — отдельное сообщение в ленте
  своего лида, у каждой своя личная ссылка.
- **Два вида содержания**:
  1. «Рассказать о решении» (например `/solutions/plitka`,
     `/works/sfery/plitka`): письмо по шаблону с подстановками и одной
     Презентацией на всех (у каждого получателя своя личная ссылка);
     позиций нет. Открытие — запись «открыл предложение» в ленте лида (учёт
     через страницу-переход, см. «Единый реестр «Предложения»»). Ответ
     приходит в рабочий ящик и привязывается к лиду. Открывшему — задача
     менеджеру «позвонить» (правило «задача при первом открытии» по
     настройке кампании).
  2. «КП каждому»: шаблон КП (`cms-proposal`); при запуске каждому лиду
     автоматически создаётся его КП из шаблона и отправляется. Дальше — как
     обычное КП: просмотр, «Принять», «Задать вопрос». Вручную КП никто не
     создаёт.
  В обоих случаях кампания отправляет предложение из единого реестра
  «Предложения» через «Отправить клиенту», с кодом на каждую отправку.
- **Получатели только из CRM**: иначе некуда записать отправку, открытие и
  ответ. Импорт списка (таблица/CSV) с проверкой повторов
  (`cms_company_duplicate_check` и аналог для лидов), источником «Рассылка»,
  отметкой о согласии и её основанием. Стоп-лист и «отписаться» — при любой
  отправке кампании.
- **Каналы кампании**:
  - малые объёмы (десятки писем) — ящик менеджера как обычные личные письма
    с ограничением скорости (по умолчанию не больше ~30 в день с ящика,
    паузы между письмами); ответы приходят сами;
  - сотни и тысячи по своей базе с согласием — сервис рассылок (Unisender Go
    и аналоги) через API, события доставки и отписки по вебхуку, ответы — в
    рабочий ящик через `Reply-To`.
- **Холодные рассылки** (база собрана самостоятельно, согласия нет): сервисы
  рассылок (Unisender) их запрещают и блокируют аккаунт; 38-ФЗ требует
  предварительного согласия на рекламную рассылку. Поэтому через сервис —
  только своя база с согласием. Холодные контакты — только небольшими
  персональными письмами от менеджера, по возможности с отдельного домена
  (не портить репутацию основного), с отпиской и стоп-листом; кампания
  помечает получателей без согласия и не даёт отправить их через сервис.

**Служебные и рекламные сообщения, темы, согласие, отписка** (согласовано с
владельцем 23.10.2026, этапы 4 и 7).

| | Служебные | Рекламные (рассылки) |
|---|---|---|
| Примеры | счёт заканчивается, услуга истекает, КП по запросу, ответ по задаче | новое решение, акция, новости студии, холодное предложение |
| Этап | 7 «Уведомления клиентам» | 4 «Рассылки» |
| Согласие | не нужно | нужно (38-ФЗ), кроме холодных писем менеджера |
| Отписка | нет; клиент выбирает только канал получения | по темам, ссылка в каждом письме и `List-Unsubscribe` |

- **Отписка от рекламы никогда не отключает служебные сообщения.** Личные
  письма менеджера отписка не блокирует, а показывает предупреждение.
- **Темы рассылок** заводятся в настройках («Новые решения и услуги», «Акции
  и скидки», «Новости студии», «Новости платформы»). У каждой кампании одна
  обязательная тема.
- **Согласие и отписка хранятся у контакта** — адреса почты, номера
  телефона, позже чата бота — по каждой теме, а не у лида: один адрес бывает
  у лида, компании и клиента одновременно, а согласие на почту не означает
  согласия на СМС. У согласия — основание («подписался на сайте», «дал
  согласие устно», «нет согласия — холодный контакт»), дата и кто отметил.
- **Отписка относится к контакту, через который пришла рассылка**: ссылка в
  письме отписывает этот адрес, «СТОП» на СМС — этот номер, кнопка бота —
  этот чат. Страница отписки показывает темы галочками (отписаться от одной
  или от всех) и пункт «отписаться от всех рекламных рассылок по всем
  каналам» — тогда отписываются все контакты лида, компании или клиента.
- **В карточке** лида, компании и клиента у контакта видно состояние
  подписки по темам.
- **Кампания перед запуском** показывает исключённых и причину: отписан от
  темы, нет контакта, нет согласия для выбранного канала (для сервиса
  рассылок согласие обязательно).
- **Этап 7** даёт клиенту выбор каналов служебных сообщений на тех же
  контактах, без отписки.

## Отправить клиенту

Согласовано 23.10.2026 (этап 3, мини-сессия A). КП, счета, акты, позже
уведомления этапа 7 отправляются клиенту любым каналом, поэтому отправка — общая
точка `cms-communication`, а не код каждого пакета.

- **Отправляемое** описывает пакет (КП, счёт): название, короткий текст,
  личная ссылка (создаётся на каждую отправку — пакет получает канал и
  получателя и возвращает ссылку со своим кодом), файлы (PDF), запись в CRM, к
  которой относится отправка (лид, компания, сделка, клиент).
- **Окно «Отправить клиенту»**: контакты клиента из CRM (email, телефоны,
  позже привязанные боты), выбор канала и получателя, предпросмотр текста,
  правка текста менеджером. Видимость записей — `forManager()`.
- **Канал сам решает вид**: письмо — текст, кнопка «Открыть …», PDF
  вложением, уходит из ящика менеджера как обычное письмо (лента, переписка,
  «Отправленные»); СМС — короткий текст и ссылка через провайдеров СМС
  `skeeks/cms`; Telegram и MAX — кнопка и файл (этап 5, без переделки
  отправляемого). Канал возвращает созданное сообщение, пакет хранит его в
  своей записи отправки.
- **«Прикрепить из…» в форме письма** («источник вложений»): пакеты добавляют
  пункты («КП», потом «Счёт»); выбранное вставляется в письмо личной ссылкой
  и файлом, а пакет получает отметку об отправке, как из окна «Отправить
  клиенту».
- Ограничение получателей стенда (`allowedRecipients`) действует для всех
  каналов, для СМС — свой список номеров.

## КП (реестр предложений)

Согласовано 23.10.2026 (этап 3). Пакет `skeeks/cms-proposal`.

**Берём готовое**: позиции и итоги как у счёта `cms-shop` (`ShopBillItem`:
наименование, единица, количество, цена, скидка, сумма, `vat_name`, НДС не
считается — только надпись); PDF через mPDF, как счёт и отчёт по задаче,
оформление — шаблон документов сайта `CmsDocumentTemplate` (логотип, цвета,
тема); страница по секретному коду без входа, как у счёта; создание из лида,
сделки, компании — `Skeeks::$recordSources` (`?source=`); лента —
`logRenderers`, уведомления — `CmsWebNotify`; реквизиты нашей компании
копируются в версию, как в счёт (`fillContractorSnapshot`).

**Модель**:
- КП — номер, название, клиент (лид, компания или сделка — любой из трёх;
  КП лида видны в карточке его компании), ответственный, статус (черновик,
  отправлено, открыто, принято, отклонено, истекло), срок действия (по
  умолчанию 14 дней), валюта, текущая версия.
- Версия — содержимое: вступление и условия (общий редактор текста, картинки
  можно), позиции с разделами, итог и скидка, реквизиты. Отправленная версия
  не меняется: правка после отправки создаёт новую версию. PDF версии
  делается при первой отправке и хранится с ней.
- Позиция — как строка счёта, с необязательной ссылкой на товар/услугу
  `cms-shop`, если пакет установлен.
- Отправка — версия, канал, получатель, сообщение CRM, секретный код ссылки,
  кто и когда отправил, первый и последний просмотр, число просмотров.
- Просмотр — время, отправка, браузер (для истории и отсева роботов).
- Шаблоны КП — готовые наборы текста и позиций («Сайт под ключ», «SEO»,
  «Хостинг»); новое КП делается из шаблона.

**Страница КП для клиента**: позиции, итог, условия, «Скачать PDF»,
«Принять», «Задать вопрос». Ссылка показывает отправленную версию; если
отправлена более новая — плашка «Есть обновлённое предложение». После срока —
«Предложение истекло, свяжитесь с менеджером». «Принять» меняет статус,
пишет в ленту, уведомляет менеджера; счёт автоматически не создаётся —
менеджер выставляет его кнопкой «Выставить счёт» (позиции переносятся в
счёт `cms-shop`). «Задать вопрос» создаёт сообщение в переписке клиента: входящее «Сообщение
с сайта» без ящика (`services\SiteMessages`, канал `site`, переписка
`site:proposal:<id>`), связанное с клиентом КП и его компанией; ответ —
обычным письмом на адрес, куда отправляли КП.

**Честное «открыто»**: почтовые проверки ссылок, предпросмотр Telegram и MAX,
антивирусы открывают ссылку раньше клиента. Просмотр засчитывается только
сигналом из самой страницы после её показа в браузере; известные роботы
предпросмотра не считаются. Первый просмотр — запись «КП открыто» в ленте и
уведомление менеджеру.

**В CRM**: раздел «КП» (список, фильтры по статусу и менеджеру), блок «КП» в
карточках лида, компании и сделки с кнопкой «Создать КП», записи ленты «КП
отправлено (канал)», «КП открыто», «КП принято».

**Отложено**: блоки «О нас», кейсы и портфолио внутри КП; электронная
подпись; расчёт НДС.

**Необязательные позиции и выбор клиента** (согласовано 23.10.2026, этап 3,
шаг D). Позицию или раздел КП можно отметить «на выбор клиента» (включено или
выключено по умолчанию). На странице КП клиент включает и выключает их
галочкой, итог пересчитывается сразу; в итоге и PDF видно, что входит, а что
предлагается дополнительно. «Принять» сохраняет выбранный вариант в отправке
(состав и сумма на момент принятия), он виден в карточке КП и в ленте
(«КП принято: с продвижением»). Сама версия не меняется. «Выставить счёт»
переносит в счёт только выбранные позиции.

**Единый реестр «Предложения»: КП и Презентация** (согласовано с владельцем
23.10.2026, этап 3, шаг E; заменяет прежнюю идею отдельного отправляемого
«страница сайта» в `cms-communication`). Нам важен факт открытия нашей
личной ссылки; что показать после — дело вида предложения. Поэтому одна
сущность `cms-proposal` с видом:

| Вид | Что внутри | Что видит клиент по ссылке |
|---|---|---|
| КП | позиции, версии, итог, условия, «Принять», «Задать вопрос» | страница КП |
| Презентация | адрес страницы (своего сайта или любой, например `/works/sfery/plitka`, `/solutions/plitka`) и короткий текст менеджера | страница-переход: засчитывает просмотр и сразу переводит на страницу |

Отправка, личные ссылки, отправки по каналам, учёт просмотров, лента,
уведомления, правила и кампании этапа 4 — общие для обоих видов. Менеджер:
«Создать предложение» → вид → «Отправить клиенту». Кампания всегда
отправляет предложение: каждому лиду своё КП из шаблона или одну и ту же
презентацию.

Оговорки:
1. **Своя форма у каждого вида.** Вид выбирается первым; у Презентации нет
   позиций, версий и «Принять» — только адрес, название, текст менеджера
   (срок действия по желанию). Пустых полей КП в ней не показывать.
2. **Адрес перехода хранится в предложении**, никогда не берётся из
   ссылки: страница-переход не должна стать открытым перенаправлением
   (фишинг от имени нашего домена). Разрешённые адреса — `http(s)`; чужие
   домены допустимы, но сохраняются только сотрудником.
3. **Метки для Метрики.** При переходе к адресу добавляются
   `utm_source=crm`, `utm_medium=<канал>`, `utm_campaign=<номер предложения
   или кампании>` (не затирая уже указанные метки), иначе визиты выглядят
   прямыми заходами.
4. **Отсев проверок ссылок.** Просмотр засчитывается сигналом из страницы
   после её показа (роботы предпросмотра без скриптов не засчитываются и
   никуда не переходят). Защитные системы, которые открывают ссылку в
   настоящем браузере (проверка ссылок Outlook и подобные), отсеиваются по
   признакам: открытие в первые секунды после отправки, адреса
   дата-центров, известные браузерные отпечатки. Такое открытие в ленте
   помечается «возможно, проверка ссылок», статус «открыто» и уведомление
   оно не даёт.
5. **Кнопка «Связаться» на целевой странице — позже.** После перехода на
   `/works/sfery/plitka` у клиента нет «Задать вопрос»; пока менеджер
   звонит по уведомлению или задаче. Следующий шаг (вне этапа 3): на наших
   сайтах запоминать код перехода, показывать «Связаться с менеджером» и
   писать в ленту лида, что он смотрел дальше.

**Правило «задача менеджеру при первом открытии»** (согласовано
23.10.2026, этап 3, шаг E). При первом засчитанном открытии предложения
любого вида ответственному ставится задача «Позвонить: клиент открыл
предложение №…» на сегодня (вне рабочего времени — на ближайший рабочий
день), привязанная к лиду/компании/сделке и к предложению. Включается
настройкой (по умолчанию включено для отправок менеджером, для кампаний —
настройкой кампании). Повторные открытия задачу не создают; если у
ответственного уже есть открытая задача по этому предложению — не создаётся
новая. Открытия, помеченные «возможно, проверка ссылок», задачу не ставят.
Сделано так (шаг E): правило срабатывает на первом засчитанном просмотре
каждой отправки, поэтому новая отправка, открытая после выполненной задачи,
даёт новую задачу; метка кампании в адресе — `utm_campaign=proposal-<номер>`
(у кампаний этапа 4 будет `campaign-<id>`).

**Сценарий: звонок → презентация → КП** (согласовано 23.10.2026). Так
менеджеры работают с готовыми решениями.
1. После звонка менеджер отправляет клиенту Презентацию (страница решения
   или сферы, например `/works/sfery/plitka`): общую, созданную один раз
   для всех, или созданную для этого клиента. Письмо как
   сейчас, но ссылка личная: в ленте видно, открыл ли клиент и когда, при
   открытии менеджеру ставится задача «Позвонить».
2. Если клиент заинтересовался — КП из шаблона решения («Сайт для магазина
   плитки»): во вступлении кнопка «Подробнее о решении» на страницу решения
   (описание не повторяется), основные позиции — сайт, «Продвижение» —
   необязательный раздел, который клиент включает сам (шаг D).
3. «Принять» фиксирует выбранный вариант, менеджер выставляет счёт на него.

## Стенд skeeks.com (Windows)

- Пакеты стоят из боевого `composer.lock`, а `link-shared-vendor.php`
  заменяет их ссылками на общий вендор: правки в
  `C:\SkeekS\dev\php\vendor\skeeks\cms-communication` сразу видны стенду
  (быстрый профиль и Compose Watch). Новые миграции — `cms/migrate`, затем
  очистка `frontend/runtime/cache`; после правки задач — перезапуск
  `worker-communication`.
- Обработчик очереди — сервис `worker-communication` в `compose.fast.yaml`.
  Расписания на стенде нет: письма забираются кнопкой.
- `docker/config/main-dev.php`: ключ шифрования стенда и
  `communication.allowedRecipients = ['@skeeks.com']` (база — копия боевой).
  После правки — `docker compose -f compose.yaml -f compose.fast.yaml restart worker-communication`.
- Тестовый ящик — sem-ov2007@yandex.ru (пароль приложения вводит владелец).
  Для проверки уведомлений у пользователя 1 на стенде есть строка прав
  «все письма» на этот ящик (22.10.2026).
