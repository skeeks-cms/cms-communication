# Архитектура коммуникаций

Согласованный проект (октябрь 2026). Пока это план: пункты становятся
контрактом по мере реализации и проверки. Исполняемый код — окончательный
источник истины.

## Цель

Полная картина взаимодействия с клиентом в CRM: кто, что, когда отправил,
кто позвонил, в какой последовательности, человек это был или ИИ. Менеджер
не уходит в другие сервисы: звонит из карточки лида, отсюда же отправляет
письмо или КП, видит ответ в ленте.

## Главные принципы

1. **Одна операция — один сервис.** Ответить, создать задачу из сообщения,
   привязать к компании — одна серверная операция. Её вызывают интерфейс,
   инструменты `cms-mcp`, сценарии бота и ИИ.
2. **ИИ — такой же исполнитель, как менеджер.** Отдельный пользователь
   «ИИ-помощник» со своей ролью и правами, действия через те же операции,
   всё записано от его имени.
3. **У каждого действия есть исполнитель**: сотрудник, ИИ, система (правило
   или расписание) или внешняя сторона.
4. **Сообщение хранится один раз**, в ленту попадает ссылка (`cms_log`),
   как у звонков.

## Доступ

- Владельца у ящика нет: права выдаются каждому сотруднику отдельно.
  Плюс «ответственные за ящик» для служебных уведомлений.
- Письмо видно, если есть чтение «всё» на ящик, или письмо привязано к
  сущности, которую сотрудник видит по `forManager()`, или он участник или
  ответственный этой переписки. У ящика есть настройка «показывать письма
  через связанные сущности» (для личных ящиков можно выключить), у
  переписки — отметка «конфиденциально».
- Отправка «только своим»: адреса видимых сотруднику лидов, компаний и
  клиентов или ответ в видимой переписке. Проверяется на сервере.
- Удаление, перемещение и «спам» меняют ящик на сервере у всех и требуют
  права «управление письмами».

## Почта

- Приём: расписание `cms-agent` на каждое подключение → задача опроса
  (`resourceKey` на подключение, повторный запуск пропускается). Забираются
  «Входящие», «Отправленные» и выбранные папки; при подключении — последние
  30 дней. «Спам» и «Удалённые» не забираются.
- Одно письмо в нескольких ящиках — одно сообщение и несколько копий.
- Цепочки: `In-Reply-To`/`References`, номер в теме, адрес `reply+<ключ>@`.
- Привязка: точное совпадение адреса с email лида, компании или клиента.
  Внутренние письма (все участники — наши адреса) не привязываются.
- Отправка: сообщение `queued` и задача отправки в одной транзакции,
  Message-ID задаём заранее. SMTP, затем копия в «Отправленные», если
  сервис не кладёт её сам. Неизвестный исход не повторяется.
- Письма, отправленные из Яндекса, Outlook или с телефона, попадают в CRM
  при опросе «Отправленных».

## Уведомления

- Сотрудникам — только `CmsWebNotify`: ответственному за переписку, иначе
  исполнителю лида, менеджерам компании, держателям чтения «всё».
  Без дублей и без уведомления о своём действии.
- Клиентам — пакеты регистрируют виды событий (счёт выставлен, услуга
  заканчивается). Правила выбора каналов: во все, по приоритету,
  с запасным каналом, обязательный + удобный, как выбрал клиент.
  Стабильный ключ события исключает повтор. В ленте одна запись со статусом
  по каналам. Тихие часы, ограничение частоты, отписка от информационных.

## Мессенджеры

- Бот — канал переписки (диалоги, «взять диалог») и мини-кабинет клиента
  (меню из пунктов, которые регистрируют пакеты; вход по ссылке из кабинета,
  по номеру телефона, по коду из СМС через существующий механизм входа;
  сложные экраны — кабинет клиента как мини-приложение).
- Групповые чаты — отдельные переписки с участниками; личные данные клиента
  в них не показываются. Чат можно связать с компанией и сделкой; для
  оживлённых чатов в ленте — только отмеченные сообщения или сводка.

## Действия над сообщением

«Создать задачу / лид / сделку», «Привязать», «Ответить». Форма создания
открывается заполненной, после сохранения появляется связь «создано из
сообщения». Статусы задачи могут уходить обратно в переписку.

## ИИ

Уровни самостоятельности: выключен, подсказывает, действует и сообщает,
полностью сам — для бота, переписки и вида действия. Если менеджер взял
диалог или ответил, ИИ молчит. Журнал решений (`cms_ai_run`). Сообщения
клиента — данные, а не команды: права инструментов ограничены привязанной
компанией и этой перепиской. Модель выбирается на уровне сайта (152-ФЗ).

## Рассылки

Рассылка создаёт обычные сообщения пачкой (`ChunkedJobHandler`), получатели
фиксируются при запуске и только из видимых менеджеру. Массово — только
через сервис рассылок, не через личный SMTP. Стоп-лист при любой отправке.
«Прочитано» надёжнее определять по просмотру КП, чем по пикселю.

## Этапы

1. Ядро и почта: точки расширения `cms`, подключения и права, приём,
   привязка, лента, «Написать» из карточек, уведомления, раздел «Почта».
2. Правила: лид или задача из письма, автоответ; создание из источника.
3. Реестр КП.
4. Рассылки.
5. Боты: переписка, затем меню, вход и уведомления клиентам.
6. ИИ.

Порядок этапов 3–6 определяется потребностями бизнеса.

## Открытые вопросы

- Хранение паролей ящиков: зашифрованы в БД ключом из параметров проекта.
  Правило вендора о секретах нужно дополнить этим случаем.
- OAuth для Яндекса, Gmail, Mail.ru — после паролей приложений.
- Возможности API MAX (кнопки, мини-приложения, группы) — сверить перед
  этапом ботов.
