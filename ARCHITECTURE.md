# Коммуникации SkeekS CMS: архитектура, решения и план

Единый документ проекта «коммуникации в CRM»: почта, мессенджеры, уведомления
клиентам, рассылки, КП, ИИ. Согласован с владельцем (октябрь 2026). Чтобы
продолжить работу в новом чате, достаточно прочитать этот файл, затем
`AGENTS.md` и `README.md` пакета. Исполняемый код — окончательный источник
истины; всё, что ещё не сделано, здесь помечено как план.

## Цель

Полная картина взаимодействия с клиентом в CRM: кто, что, когда отправил,
кто позвонил, в какой последовательности, человек или ИИ. Менеджер не уходит
в другие сервисы: звонит из карточки лида, оттуда же пишет письмо или
отправляет КП и видит ответ в ленте. Почта, боты (Telegram, MAX, ВК и др.),
СМС и звонки сходятся в одну ленту лида, компании, клиента, сделки.

## Главные принципы

1. **Одна операция — один сервис.** Ответить, создать задачу из сообщения,
   привязать к компании — одна серверная операция. Её вызывают интерфейс,
   инструменты `cms-mcp`, сценарии бота и ИИ. Логика не дублируется в
   контроллерах.
2. **ИИ — такой же исполнитель, как менеджер**: отдельный пользователь
   «ИИ-помощник» со своей ролью и правами, действует через те же операции,
   всё записано от его имени.
3. **У каждого действия есть исполнитель**: сотрудник, ИИ, система (правило,
   расписание) или внешняя сторона. Изменения только через сервисы, не прямым
   SQL — иначе журнал их не увидит.
4. **Сообщение хранится один раз**, в ленту записи попадает ссылка
   (`cms_log` типа `message`), как у звонков.
5. **Пакет необязательный.** Ядро `cms` от него не зависит; сайты без CRM его
   не ставят. Драйверы каналов — отдельные пакеты.
6. **Всё внешнее — через `cms-job`**: свои полосы, блокировки по подключению,
   без своих очередей. Неизвестный исход отправки не повторяется.

## Пакеты

| Пакет | Что в нём |
|---|---|
| `skeeks/cms` | Только точки расширения: отрисовка своих типов записей ленты (`Skeeks::$logRenderers`), типы ленты карточек (`Skeeks::$activityLogTypes`, `CmsLogQuery::activity()`, в том числе лента задачи), кнопки у телефона и email в карточках (`CrmContactBlockWidget::contactActions()` + событие), источники лида `email`, `max`, «создание из источника» (`Skeeks::$recordSources`, `source\RecordSources`, `?source=<тип>:<id>` в стандартном окне создания) |
| `skeeks/cms-backend` | Общие иконки почты в `BackendIcon` (inbox, send, reply, forward, mail-open, paperclip); исправлена зависимость скриптов ссылки на запись (`AjaxControllerActionsWidgetAsset` → `ControllerActionsWidgetAsset`) |
| `skeeks/cms-communication` | Подключения, ящики, права, переписки, сообщения, связи, лента, раздел «Почта», окно «Написать», фоновые задачи. Позже: уведомления клиентам, рассылки, сценарии ботов, шаблоны |
| `skeeks/cms-communication-imap` | Драйвер почты: свой клиент IMAP (без `ext-imap`), SMTP через `symfony/mailer`, подстановка серверов по домену и MX |
| Драйверы мессенджеров (план) | Telegram, MAX, ВК: приём событий, отправка, описание возможностей канала |
| Драйверы сервисов рассылок | `skeeks/cms-communication-unisender` (Unisender Go, этап 4C): отправка через API по одному письму, события доставки по вебхуку; позже аналоги |
| `skeeks/cms-proposal` (этап 3) | Реестр КП: версии, позиции, шаблоны, PDF, страница КП по личной ссылке с учётом просмотров, «Принять» и «Задать вопрос»; зависит от `cms` и `cms-communication`, `cms-shop` — по желанию |
| `skeeks/cms-ai` (план) | Языковые модели, правила самостоятельности, журнал решений |
| `cms-mcp` (план) | Инструменты `cms_comm_*` для внешних клиентов и ИИ |
| `cms-mobile` | Push как ещё один канал уведомлений клиентам (план) |

`cms-shop`, `cms-hosting` и другие пакеты не зависят жёстко от коммуникаций:
публикуют события и регистрируют пункты меню бота, если пакет установлен;
без него всё работает как раньше (`cms-mailer`).

## Будущий реестр файлов хранилища: почта — первый кандидат

План общего реестра использования файлов хранилища ведётся в `skeeks/cms`
(`AGENTS.md`, раздел «Planned: storage file usage registry»; согласован
21.10.2026, не начат). Почта — первый кандидат на подключение: её реестр
`cms_comm_message_file` станет поставщиком сведений «файл используется в
письмах …», остальная почта не меняется. До появления реестра почта
соблюдает два правила:
- файл письма передаётся в другой раздел копией, а не ссылкой на тот же файл
  хранилища («Создать задачу из письма» и подобное);
- уборка файлов почты (срок хранения, кэш экономного режима) удаляет файл
  хранилища, только когда на него не ссылается ни один файл письма, а после
  появления реестра — и только если общая проверка «используется ли файл»
  отвечает «нет».

## Почта: решения

**Ящик и подключение.** Для пользователя одна форма «Почтовый ящик»: адрес,
имя отправителя, логин (по умолчанию адрес), пароль приложения, серверы
(подставляются сами для Яндекса, Mail.ru, Gmail, Rambler, Outlook и доменов на
их почте по MX). В модели подключение (логин) и ящик (адрес с правами)
разделены: несколько адресов могут приходить в один логин (алиасы, пересылка
в папки) — в форме «Письма приходят в другой ящик». Отдельный раздел
подключений из меню убран.

**Пароли** хранятся зашифрованными в БД ключом из protected params
(`params['cms-communication']['secretKey']` или `CMS_COMMUNICATION_SECRET_KEY`),
в форме не показываются, пустое поле оставляет прежний. Это зафиксированное
исключение из правила о секретах (умение, `external-service-secrets.md`).

**Права сотрудника на ящик** (владельца нет, прав у каждого свой набор):
чтение — всё / только связанное / нет; отправка — любой адрес / только своим /
нет; управление ящиком; управление письмами на сервере; «по умолчанию»;
«ответственный» (служебные уведомления). Пример: info@ — Светлана и Александр
читают всё и пишут; новый менеджер — «связанное» + «своим» и info@ по
умолчанию: видит и пишет только своим лидам.

**Раздел «Почта»** открыт каждому сотруднику с доступом в админку
(`permissionNames` — только общее право «Доступ к системе
администрирования» `CmsManager::PERMISSION_ADMIN_ACCESS` в
`AdminCmsCommMessageController` и `AdminCmsCommTemplateController`; не
`permissionName = null` — тогда право раздела создаётся только для
администраторов; и не пустой список — тогда права не проверяются вовсе и
гость получает ошибку вместо страницы входа, исправлено в 1.1.1). **Видимость письма**: чтение «всё» на его ящик,
или он отправил письмо, или письмо привязано к лиду/компании/клиенту, которых
он видит по `forManager()` (если у ящика включено «показывать через связанные»;
для личных ящиков можно выключить). Отправка «только своим» проверяется на
сервере.

**Администратор в почте — по общим правилам** (решение владельца
23.10.2026): что он читает, с каких ящиков пишет и какими письмами
управляет, задают его собственные строки доступа к ящикам, а не роль
(`forManager()`, `MailFolders::accounts()`, `MailComposeService`,
`MailboxActions`, `MessageSorting`). За ролью остаются настройка ящиков и
подключений, права сотрудников, «Настройки почты», «Сбор писем», очистка и
сохранение файлов, общие шаблоны ящиков. Чтобы видеть ящик целиком,
администратор выдаёт себе доступ, как любому сотруднику.

**Скрыто по умолчанию** (решение владельца 23.10.2026, интерфейс
перегружен): «Ответственный» за переписку — меню в письме, строка в шапке,
«Назначить меня» в меню строки, папка «Мне назначено», фильтр и метка в
строке (письмо, требующее работы, становится задачей); фильтр «Привязка» —
его заменяют папки «Мои клиенты» и «Без привязки». Данные и операции
остались; сайт включает их `communication.showAssignee` и
`communication.showLinkedFilter`. Фильтр, уже стоящий в адресе списка,
показывается, чтобы его можно было снять.

**Приём**: «Входящие» + «Отправленные» (по отметке `\Sent` или названию),
30 дней при первом приёме, дальше по UID. Одно письмо в нескольких ящиках —
одно сообщение. Письма, отправленные из Яндекса, Outlook, с телефона,
забираются из «Отправленных». Расписание — раз в 2 минуты; кнопка «Проверить
новые письма».

**Сбор писем** (карточка ящика → «Сбор писем», только администратор): письма
«Входящих» и «Отправленных» за 3 месяца … 3 года, все или с даты — задача
`comm.mail.history` (`MailHistoryJobHandler`), только чтение. Каждое письмо
принимается обычным `MailIngestService::ingest(..., history: true)`: привязка
к лидам, компаниям, клиентам и лента по дате письма, но `is_history = 1` —
считается прочитанным (не входит в счётчики, без «Не прочитано»; будущие
уведомления о новых письмах такие письма пропускают). Граница папки — курсор
обычного приёма (`cms_comm_sync_state.last_uid`), у ни разу не принимавшейся
папки — начало окна `initialDays`: новые письма остаются приёму и приходят
непрочитанными. Уже известные письма пропускаются по месту на сервере без
загрузки, затем по Message-ID, поэтому повторный или более широкий сбор ничего
не задваивает. Задача идёт порциями по 2 минуты: курсор (папка, UIDVALIDITY,
последний UID, граница) сохраняется с прогрессом, между порциями блокировка
ящика `comm-connection:N` свободна, и обычный приём проходит. Файлы писем
старше `keepDays` при приёме не сохраняются в CRM (догружаются из ящика при
открытии) — иначе их сохранила бы и на следующий день удалила уборка.

**Привязка**: точное совпадение адреса с email активного лида, компании,
клиента (не сотрудника); ответ с другого адреса — по цепочке. «Наши» адреса —
ящики, сотрудники и любые адреса на доменах наших ящиков (кроме общих
сервисов: gmail.com, yandex.ru и т. п.); письма, где все участники наши,
считаются внутренними и не привязываются.

**Отправка**: письмо `queued` и задача в одной транзакции, Message-ID задаём
заранее; SMTP ящика; затем копия в «Отправленные». Яндекс сам SMTP-письма в
«Отправленные» не кладёт и не умеет искать по заголовку — проверяем последние
письма папки. Через личный SMTP массово не слать.

**Показ письма**: HTML со своими стилями во фрейме без скриптов и форм;
вырезаются скрипты, фреймы, формы, обработчики, `javascript:`. Внешние
картинки, фоны и `url()` скрыты до «Показать картинки» (иначе отправитель
узнаёт об открытии, срабатывают служебные ссылки, а зависшая картинка-счётчик
держала панель 30 секунд). Письмо вставляется после открытия панели.

**Интерфейс «Почта»** (главное меню): слева «Написать», «Проверить новые
письма», папки «Все письма», «Мои клиенты», «Без привязки» и ящики с чтением
«всё» («Входящие», «Отправленные»), у папок счётчики непрочитанных. «Мои
клиенты» — письма, привязанные к лидам, компаниям и клиентам, которые
сотрудник видит в CRM (`linkedToVisible()`), а не любые привязанные письма
читаемого ящика; метки CRM в списке и в письме тоже только видимые ему
(`MailUi::visibleLinks()`): ссылка на карточку без доступа запускала бы её
единственное действие «Удалить». Список как
в Яндекс Почте: флажок, кружок с инициалами, отправитель, точка «не прочитано»,
тема + начало текста, метки CRM, скрепка, дата; выбор писем, «Прочитано»/«Не
прочитано». Письмо — в стандартной панели справа: «Ответить», «Переслать», «Не
прочитано», отправитель, «Кому», справа записи CRM (логотип, открывают
карточку записи). Свои CSS/JS на переменных темы, иконки — `BackendIcon`
(недостающие «ответить всем» и «картинка» пока нарисованы в `MailUi` тем же
стилем; перенос в `BackendIcon` — только по согласованию, это общий слой).

Устройство экрана: прокручивается страница, а не список; папки и шапка списка
— `position: sticky` под шапкой админки (`--sx-shell-top-offset`). Общая
обёртка `.sx-main-wrapper` в `cms-backend` режет переполнение `overflow:
hidden`, что ломает sticky, поэтому только на странице почты стоит
`.sx-main-wrapper:has(.sx-mail) { overflow: clip }` в `mail.css`. Если такое
понадобится другим разделам — менять общую оболочку по согласованию.
Порции списка: `mail?portion=2&before=<дата>&before_id=<id>` отдаёт JSON со
строками (`_rows.php`). Открытое письмо одно: следующее заменяет панель.

**Форма письма** (`create`): GET — форма (`?inline=1` — только форма для
вставки под письмом), POST — JSON `{success, id}` или `{errors}`. Параметры:
`to`, `context_model_code/_id`, `reply_to` (+`all=1` — ответ всем, без наших
ящиков), `forward`. Редактор текста — общий лёгкий виджет `skeeks/cms`
`RichTextInputWidget` (решение владельца 21.10.2026: CKEditor 4.4.7 из
`yii2-ckeditor` устарел; редактор, сделанный для почты, вынесен в общий и
используется в задачах, разделах, комментариях). Набор возможностей письма —
`ComposeForm::EDITOR_PRESET` (standard + выбор шрифта: шрифт выбирается
только в письмах) и `EDITOR_TOOLS` (без заголовков); абзац — `div`. Текст
чистится той же настройкой (`RichTextHtml::clean`), текстовая часть
строится из HTML (`RichTextHtml::toText`). Файлы, брошенные на зону
«Прикрепить файлом» редактора, приходят в почту событием `sx-rte:attach`;
брошенные на остальную форму — прикрепляются как раньше. Цитата
(`include_quote`) и пересылаемое письмо не входят в текст формы — их
добавляет `MailComposeService::queue()`. Скрытая копия хранится в
`bcc_list` и видна только у нас. Подсказки адресатов (`contacts?q=`) — только
то, что сотрудник и так видит (`forManager()`), работают в веб-запросе.

**Файлы писем** (`services\MailFiles`, таблица `cms_comm_message_file`:
письмо → файл хранилища, имя, `content_id`, `is_inline`). Байты — в хранилище
CMS (`Yii::$app->storage->upload()`; в очереди `cms_site_id` задаётся явно).
Файлы, загруженные в форму (вложения, перетаскивание, вставка скриншота),
ждут во временной папке CMS (`ajaxfileupload` `private_tmp_dir`,
`MailFiles::storeTemp()` поверх общего `skeeks\cms\services\TemporaryUploads`
с префиксом `mail`; токен привязан к сессии сотрудника) и переезжают в
хранилище только при отправке письма (`storeFromTemp()`). Закрытое письмо,
убранное вложение или картинка не оставляют ничего в хранилище: временную
папку раз в сутки чистит стандартный агент `ajaxfileupload/cleanup` (файлы
старше часа). Решение владельца 21.10.2026 — так же делать во всех формах с
файлами (задачи, новости), правило в умении (`resumable-file-uploads.md`).
Ссылки хранилища в интерфейсе не показываются: всё идёт через `file?id=`
(проверка, что сотрудник видит письмо) или `file?t=` (свой временный файл
этой сессии). Прямо в странице показываются
только растровые картинки по типу, который определило хранилище, остальное —
скачивание с `nosniff`. Картинка в тексте при отправке становится частью
письма (`DataPart::asInline()->setContentId()`), в HTML — `src="cid:…"`; при
показе `MailHtml::sanitize()` подменяет `cid:` ссылками на файлы письма.
Редактор отдаёт картинки как `<img data-sx-upload="токен">` (загрузка — через
почтовое `upload` с правом отправки и пределом 25 МБ), очистка пропускает
только такие картинки и стили панели с проверкой значений.
Предел — 25 МБ на файл и на все вложения письма (`MailFiles::MAX_SIZE`);
больше — у входящих сохраняется только имя. Письмо не уходит, если файла нет
в хранилище. Скрытая копия проверяется настройкой `allowedRecipients`
наравне с «Кому» и «Копией».

Одинаковое содержимое хранится один раз на сайт: у файла письма есть
`content_hash` (SHA-256) и размер; при приёме (`MailFiles::storeReceived()`)
и при отправке своих загрузок (`storeFromTemp()`) сначала ищется уже
сохранённый файл с тем же отпечатком, и новое письмо ссылается на него
(логотипы подписей, повторные рассылки, один прайс в разных письмах). Поэтому
один файл хранилища может принадлежать многим письмам: удалять его можно,
только когда на него не ссылается ни один файл письма (удаление писем и
черновиков обязано это проверять). Удаление записи хранилища теперь не
убирает файл из писем (связь `SET NULL`): файл остаётся описанным и
подгружается из ящика.

**Хранение файлов настройками.** Общие настройки — компонент
`components\MailFileSettings` на уровне сайта (по правилам
`component-settings.md`: на основном сайте запись по умолчанию), страница
«Настройки почты» → «Хранение файлов» (`AdminCmsCommSettingsController`,
только администратор). У ящика — `cms_comm_account.file_settings` (JSON,
null — как в общих), блок «Хранение файлов» в его карточке. Действующие
правила — `services\MailFilePolicy`: по умолчанию «Минимальный» (22.10.2026);
режим «Полный» (всё у себя),
«Экономный» (картинки у себя, вложения из ящика), «Минимальный» (всё из
ящика), «Выборочно»; порог размера; `keepDays` — срок копий по дате
письма (по умолчанию 365 дней, удаляет ежедневная уборка; 0 — всегда); `cacheDays` — срок копии, подгруженной по запросу,
после последнего открытия. Письмо в нескольких ящиках следует самому
«хранящему» из них. Текст письма хранится всегда. Форма показывает только
нужное режиму: порог и `keepDays` — когда что-то хранится, `cacheDays` —
когда что-то берётся из ящика (его нет у «Полного» и «Выборочно» со всеми
отметками без порога размера). Форма настроек сайта имеет свой id
(`sx-mail-file-settings`): форма таймера работы в шапке тоже `w0`, и
динамическая перезагрузка поля по `#w0` отправила бы таймер.

**Файл без копии в CRM** — строка `cms_comm_message_file` с
`storage_file_id = null`, номером файла в письме `part_index`, размером и
отпечатком. При приёме строка создаётся всегда, байты сохраняются, только
если правила ящика это разрешают (уже сохранённое одинаковое содержимое
переиспользуется в любом режиме). Подгрузка — задача
`comm.mail.fetch-files` (`MailFileFetcher`, через `cms-job`, не в
веб-запросе): письмо читается заново только для чтения по папке и UID копии
(`cms_comm_message_mailbox`), при другой UIDVALIDITY считается
недоступным; файл находится по `part_index` с проверкой имени и размера,
затем по Content-ID. Если правила ящика такой файл хранят (письмо, принятое
до сохранения файлов, в «Полном» режиме), копия остаётся навсегда; иначе
помечается `is_cached` и `last_access_at` и уходит через `cacheDays`. Экран
письма сам запрашивает картинки текста, вложение — по нажатию, затем
скачивание; страница опрашивает `fetch-status` (готовность файлов и
`pending` — идёт ли задача). У писем, полученных до сохранения вложений,
первая подгрузка описывает все их файлы. Пересылка и цитата сначала
подгружают недостающие файлы исходного письма. Отправленное из CRM письмо
получает место на сервере, когда приём находит его в «Отправленных»
(`addCopy` дописывает папку и UID).

**Сохранить файлы в CRM** («Настройки почты», только администратор) —
обратное очистке: ящик, срок писем (как в «Сборе писем»), картинки и/или
вложения, порог размера; «Посчитать» (`MailFileSave::preview`: сколько
загрузить и их размер по `size` строк, сколько временных копий станет
постоянными), затем задача `comm.mail.save-files`
(`MailSaveFilesJobHandler`). Задача идёт по письмам по возрастанию id:
временная копия только перестаёт быть временной, недостающие файлы
загружаются `MailFileFetcher` (`onlyIds`, `keepForGood`) — одно чтение письма
на все его файлы, одна IMAP-сессия на подключение на всю порцию; порции по
2 минуты с курсором. Блокировку ящика не берёт (только чтение), приём идёт
рядом. Срок `keepDays` действует и на сохранённое: страница предупреждает, если
выбранные письма старше него. Проверено на стенде: после ручной очистки 65
файлов задача вернула их все (и 4 временные сделала постоянными), отпечатки
совпали.

**Очистка** — задача `comm.mail.cleanup-files` (`MailFileCleanup`):
ежедневно по агенту (`auto` — `keepDays` и `cacheDays` каждого ящика) и
вручную администратором («Очистка файлов»: старше N дней, вложения и/или
картинки, больше N МБ, ящик; сначала «Посчитать», затем запуск со ссылкой на
ход выполнения). Удаляется только копия в CRM (`MailFiles::forget()`; сам
файл хранилища — когда на него не ссылается ни одно письмо), строка письма
остаётся. Никогда не удаляется копия письма без известного места на сервере
(отправленное, ещё не найденное в «Отправленных», или удалённое из всех
ящиков): там копия в CRM единственная.

**Подписи и шаблоны** (`services\MailTemplates`, 22.10.2026). «Мои
настройки почты» (`admin-cms-comm-message/personal`, ссылка под папками
«Почты» и пункт меню «Шаблоны» в форме письма): уведомления по ящикам,
подпись для каждого ящика с правом отправки (общий `RichTextInputWidget`),
список шаблонов. Подпись подставляется в новое письмо, ответ, пересылку и
быструю строку ответа блоком `data-sx-mail-signature` под пустой строкой,
то есть над цитатой (цитату добавляет сервер при отправке); смена «От
кого» заменяет блок подписью другого ящика или убирает его. Черновик подпись
не подставляет повторно (атрибут блока сервер вычищает, после повторного
открытия подпись — обычный текст). Шаблон — личный (виден только автору, в
любом ящике) или общий для ящика (всем, кто пишет с него; добавлять и
менять — тем, у кого «Управление ящиком», и администраторам); добавляются и
меняются в стандартных окнах `AdminCmsCommTemplateController` (открывается
только то, что сотрудник может менять; выбор «Кому доступен» — виртуальное
поле `scope`, так как select2 теряет подпись пустого значения). Вставка — в
место курсора, иначе в начало текста над подписью. Подписи и шаблоны чистятся
`MailTemplates::EDITOR_PRESET` — форматирование письма без картинок:
временные загрузки истекли бы в сохранённом тексте (картинки в подписях —
план).

**Черновики** (`services\MailDrafts`, 22.10.2026). Форма письма сохраняет
себя через 2 секунды после изменения (`draft`, только один запрос за раз,
повтор после него) и при закрытии окна (`sendBeacon`); пустое заполнение
формы (адресат ответа, подпись) черновиком не считается. Адресаты хранятся
как набраны, письмо проверяется только при отправке; сохраняются только
свой ящик, видимые письма и записи CRM. Черновик ответа помнит письмо
(`reply_to_message_id`, «Ответить всем»): «Ответить» на этом письме
продолжает его, строка ответа пишет «Продолжить черновик ответа». Файлы:
форма работает с временными загрузками сессии; при сохранении каждая новая
загрузка копируется в хранилище (`cms_comm_draft_file`, одинаковое
содержимое писем и черновиков переиспользуется, временный файл остаётся у
открытой формы), при открытии черновика в другой сессии байты снова кладутся
во временную папку под новым токеном, текст черновика сразу получает новые
токены. Отправка удаляет черновик (файлы, взятые письмом, остаются у
письма), «Удалить черновик», крестик в папке и «Отменить» под письмом —
тоже. Файл хранилища удаляется, только когда на него не ссылается ни письмо,
ни черновик (`MailFiles::deleteUnused()`, им пользуется и уборка файлов
писем). Ежедневная уборка `comm.mail.cleanup-files` (`auto`) удаляет
черновики, которые не меняли «Хранить неотправленные черновики, дней»
(«Настройки почты» → «Хранение файлов», по умолчанию 90, 0 — не удалять).

## Мессенджеры и боты

### Этап 5: решения (согласовано с владельцем 24.10.2026)

**Пакеты.** Общее — в `cms-communication`: модели, приём, отправка, раздел
«Чаты», привязки, права, MCP. Драйверы — отдельные пакеты
`cms-communication-telegram` и `cms-communication-max`, как
`cms-communication-imap`: разбор события в общий вид, отправка, файлы, кнопки,
возможности канала, вебхук и опрос. Для тестов — поддельный драйвер в пакете.

**Бот = ящик.** Подключение бота — `cms_comm_connection` с драйвером
мессенджера (токен — секрет подключения, свой секрет вебхука, режим «вебхук» /
«опрос»). К нему — `cms_comm_account` с адресом `@ник бота`: права сотрудников
(`cms_comm_account_access`: читать всё/связанное, писать, управлять,
уведомлять), карточка и «по умолчанию» берутся у почты. Настройка ботов —
только администратор.

**Модель данных.**
- `cms_comm_identity` — собеседник в мессенджере: сайт, канал, внешний id
  пользователя (уникально), имя, ник, подтверждённый телефон, связь с
  пользователем CMS (клиент или сотрудник), способ и время привязки, кто
  привязал, «заблокировал бота». Собеседник-сотрудник — сообщения «от нас».
- `cms_comm_participant` — участники группового чата: переписка, собеседник,
  роль, вошёл, вышел.
- Переписка — существующая `cms_comm_conversation`: канал `telegram`/`max`,
  `thread_key` `<подключение>:<id чата>`; новые поля — подключение, вид
  чата (`private`/`group`/`channel`), внешний id чата, название, состояние и
  права бота в чате. «Взять диалог» — существующий ответственный за
  переписку (`assigned_user_id`).
- Сообщение — существующее `cms_comm_message` (канал, направление, статус):
  `external_id` — `<подключение>:<id чата>:<id сообщения>` (бот в ключе:
  Telegram нумерует сообщения у каждого бота, а id личного чата — id
  человека, поэтому у двух ботов сайта id совпадают); новые поля — автор
  (`cms_comm_identity_id`), ответ на сообщение, изменено/удалено в
  мессенджере. Файлы — `cms_comm_message_file`, как у писем.
- `cms_comm_bot_update` — журнал сырых событий: подключение, ключ события
  (уникально на подключение), JSON, состояние (новое, применено, пропущено,
  ошибка), попытки, ошибка. Хранится 30 дней.
- `cms_comm_conversation_link` — привязка всего чата к компании, сделке,
  проекту (кто и когда); сообщения получают связи по ней.
- `cms_comm_link_token` — одноразовый ключ привязки (`?start=`): цель (запись
  CRM), срок, кем создан, кем использован.
- Контакт рассылок `cms_comm_contact` получает вид «чат бота» (отписка
  кнопкой бота, этап 5.5).

**Приём.** Адрес вебхука `/~comm-bot/<id подключения>`. Обработчик сверяет
секрет (`hash_equals`; Telegram — `X-Telegram-Bot-Api-Secret-Token`, MAX —
`X-Max-Bot-Api-Secret`), одной вставкой сохраняет сырое событие (повтор
отсекается уникальным ключом) и сразу отвечает 200, затем будит задачу
`comm.bot.apply` (блокировка `comm-connection:N`). Ошибка записи — 500,
мессенджер повторит. Задача разбирает события по порядку получения через
драйвер: собеседник, переписка, участники, сообщение, файлы (скачиваются
отдельной задачей сразу: срок ссылок MAX не описан, Telegram отдаёт до
20 МБ), привязки, уведомления, команды. Ошибка — отметка у события, повтор,
журнал в карточке бота. Ключ события: Telegram — `update_id`; MAX (номера
события нет) — `update_type` + `mid` (+ `timestamp` для правок,
`callback_id`, `chat_id`+`timestamp` для `bot_started`). Правка или удаление
могут прийти раньше сообщения — ждут его. Режим опроса (`comm.bot.poll`) —
для сайтов без публичного HTTPS: курсор (`offset`/`marker`) сохраняется в
одной транзакции с событиями. Вебхук и опрос взаимоисключающие на обеих
платформах. Сверка подписки раз в час (`comm.bot.subscription`): MAX сам
отключает вебхук после 8 часов неудач, Telegram хранит события 24 часа.

**Отправка.** Сообщение `queued` и задача `comm.bot.send` в одной транзакции;
скорость по чату и боту (MAX — 2 сообщения/с в чат, 30 запросов/с; Telegram —
1/с в чат, 20/мин в группу, 30/с), ответ 429 и `retry_after`. Неизвестный
исход не повторяется. Длинный текст режется по лимиту канала (MAX 4000,
Telegram 4096). Простое оформление (жирный, курсив, ссылка) переводится в HTML
канала. Подпись менеджера — первая строка «Имя (SkeekS):», отключается в
настройках бота. Бот не получает событий о своих сообщениях, поэтому всё, что
бот пишет, должно уходить через CRM — иначе его нет в переписке.

**Стенд и боевые боты** (решение владельца 24.10.2026: тестовых ботов нет,
работаем с боевыми). Стенд никогда не ставит вебхук, не опрашивает
`/updates`/`getUpdates` боевого бота, у которого на проде включён вебхук, и
не сдвигает курсор: настройка `communication.botReceive = false` на стенде
(ставить подписку и опрашивать нельзя), события на стенд — через поддельный
драйвер, записанные события и чтение истории (`GET /messages` MAX — курсор не
трогает). Отправка со стенда — только в чаты из `communication.allowedChats`
(аналог `allowedRecipients`; пусто при заданном `allowedRecipients` — ничего
не уходит) и только после «да» владельца на конкретный текст. Токен на
стенде вводит владелец (ключ шифрования стенда свой — боевые токены из копии
базы не расшифровываются). Новый бот Telegram до запуска вебхука на проде
можно опрашивать со стенда.

**Диалоги — раздел «Чаты»** (пункт меню под «Почтой»): папки «Новые» (не
взяты), «Мои», «Группы», «Все», папки ботов; в чате — лента, ответ с файлами,
«Взять диалог», «Передать», «Закрыть», привязки, участники, метка «ждёт ответа
N минут». Уведомления: новый невзятый личный диалог — сотрудникам с правом и
отметкой «уведомлять»; взятый — тому, кто взял; группа — менеджерам
привязанной компании.

**Лента.** Личные диалоги — каждое сообщение (как письма). Шумные группы —
сводка за день (сколько сообщений, кто писал, начало текстов) плюс отдельной
записью отмеченные сообщения и те, из которых создана задача.

**Привязки.** Чат к компании, сделке, проекту — окно «Привязать», как в
почте, плюс подсказка по названию чата «Компания / сайт.ru» (домен = сайт
компании). Собеседник к клиенту: «Пригласить в бота» в карточке (личная ссылка
`?start=<одноразовый ключ>`, без персональных данных; MAX ≤ 128 символов,
Telegram ≤ 64 `A-Za-z0-9_-`), «Поделиться номером» (только свой номер:
Telegram `contact.user_id == from.id`, только в личке; MAX — `hash` и
`max_info.user_id` = отправитель), код из СМС через провайдера СМС ядра. Блок
«Мессенджеры» в карточках лида, компании, клиента: собеседники, чаты,
«Написать», «Отвязать».

**Задачи из сообщений.** Источник `message` (`Skeeks::$recordSources`)
работает и для сообщений чатов, в том числе из нескольких выбранных
сообщений. Команда в группе: `/task текст`, ответ `/task` на сообщение или
упоминание бота со словом «задача» (кириллица в командах Telegram не
допускается). Создавать могут наши сотрудники и участники чата, привязанного к
компании; ответственный — менеджер компании, отметка «из чата». Бот отвечает
номером задачи, по настройке чата пишет «принята» и «выполнена».

**«Отправить клиенту» через бота.** Каналы «Telegram» и «MAX»
(`SendChannelInterface`): текст, кнопка с личной ссылкой, PDF файлом;
получатели — привязанные собеседники и чаты записи. Рассылки через ботов —
позже (нужно согласие темы для контакта «чат бота»).

**Перенос бота MAX студии** (шаг 5.7). Сейчас вебхука нет, события читает
только Codex через `/updates` с курсором; мониторинг только отправляет

**Бот Telegram.** Бот студии — прежний @skeeksbot (решение владельца

### Исходные решения

- Подключение бота — тот же `cms_comm_connection` с драйвером; карточка бота:
  настройки, доступ сотрудников, собеседники, чаты и каналы, переписки, журнал.
- Переписка — общее понятие: личная, групповой чат, канал, цепочка писем.
  Наши сотрудники в группе — тоже собеседники («от нас»). Состав и права бота
  в чатах — по событиям мессенджера (в Telegram для чтения группы нужен
  отключённый режим приватности или права администратора; MAX сверить).
- Связь переписки с любой записью (компания, сделка, проект) через
  `cms_comm_link`; для шумных групп в ленте — только отмеченные сообщения или
  сводка за день.
- Бот как мини-кабинет: меню из пунктов, которые регистрируют пакеты
  («Мои заказы», «Счета», «Мои услуги»); ответ не привязан к мессенджеру —
  драйвер рисует кнопки по своим возможностям. Вход: ссылка из кабинета
  (`t.me/bot?start=<ключ>`), «Поделиться номером», код из СМС через
  существующий вход по коду. Данные — только подтверждённому клиенту, по
  правилам кабинета клиента; в группах личного не показываем. Сложные экраны —
  кабинет клиента как мини-приложение. Привязка видна в карточке клиента
  («Мессенджеры»), её можно отвязать.
- Свободный текст — в диалог с менеджером («взять диалог»), команды и кнопки —
  в сценарий.

## Действия в ящике и сверка с сервером

Сделано 23.10.2026 (этап 2, пункт 1). Одна операция на действие —
`services\MailboxActions` (для «Почты», будущих правил и `cms-mcp`), работа
с сервером — `services\MailServerSync` внутри задач подключения.

- **Право** — «Управление письмами» (`cms_comm_account_access.can_manage_messages`)
  на ящик копии письма; администратор может всё. Без права кнопок нет
  (`canManageAny()`, `canManage($message)`), сервер отвечает 403 или
  пропускает письмо с причиной. Метки меняют те же сотрудники.
- **Перенос — просьба, потом сервер.** `move($messages, $action, $folder)`
  (trash, archive, junk, restore — во «Входящие» или «Отправленные» по
  направлению, folder — папка ящика) записывает у копии `target_role`
  (+ `target_folder`), пересчитывает `box_state` и ставит задачу
  `comm.mail.apply` подключения. Экран сразу показывает письмо на новом
  месте: место для сотрудника — `COALESCE(target_role, folder_role)`
  (`CmsCommMessageMailbox::roleExpression()`). Просьба вернуть туда, где
  письмо лежит на сервере, отменяет невыполненный перенос. Копии других
  ящиков того же подключения с тем же местом (алиасы) переносятся вместе.
  Письмо без места на сервере (отправлено из CRM и ещё не найдено в
  «Отправленных», удалено в почте) не переносится — с причиной.
- **Задача `comm.mail.apply`** (`MailApplyJobHandler`, полоса
  `communication`, `resourceKey` `comm-connection:N` как у приёма,
  наложение `coalesce`: при работающей задаче ставится одна ожидающая)
  читает просьбы в момент запуска, группирует по исходной папке и цели,
  проверяет UIDVALIDITY, переносит `UID MOVE` (без MOVE — `UID COPY`,
  `STORE \Deleted`, `UID EXPUNGE`), новый UID берёт из `COPYUID`, без него —
  по Message-ID среди новых писем папки. Удачно — у копии новые папка, UID и
  роль; письма нет в исходной папке или сервер отказал — просьба снимается,
  у копии `sync_error`, сотруднику, который просил, — `CmsWebNotify`; письмо
  остаётся там, где оно на сервере. Приём почты делает то же в начале
  своей сверки (страховка). Драйвер без `MailManageSessionInterface` —
  просьбы снимаются с причиной.
- **Папки сервера.** `MailManageSessionInterface::folderList()`: роли по
  SPECIAL-USE (`\Trash`, `\Junk`/`\Spam`, `\Archive`, `\Sent`, `\Drafts`;
  `\Templates` — тоже черновики), без отметок — по известным именам папок
  верхнего уровня (или детей INBOX). У Яндекса нет папки архива — её, как и
  сам Яндекс, создаёт первое архивирование («Архив»). Каждая папка, кроме
  «Входящих» и «Отправленных», получает строку наблюдения в
  `cms_comm_sync_state` (роль, разделитель, `last_uid` — до какого UID
  просмотрена); эти строки — список «В папку» (входящие, архив, обычные
  папки), без обращения к серверу из веб-запроса.
- **Сверка при приёме** (`MailServerSync::reconcile()`, после приёма новых
  писем): для каждой папки, где есть копии, `UID SEARCH UID <известные>`;
  копии, которых нет, ищутся по Message-ID среди писем, появившихся в
  наблюдаемых папках после `last_uid` (при первом взгляде — за срок самого
  старого пропавшего письма, не больше 2000). Нашлось — копия переезжает;
  нет — `gone` (удалено в почте), письмо уходит из обычных папок в
  «Корзину» CRM с пометкой «Удалено в почтовом ящике». Письмо, вернувшееся
  во «Входящие» или «Отправленные», принимается заново по Message-ID, и
  копия занимает новое место (`MailIngestService::addCopy()`), поэтому
  письма не задваиваются; копия в другой папке приёма (письмо себе) остаётся.
  Проверено на стенде: письмо, перенесённое в Яндексе в «Спам», а затем
  обратно, в CRM прошло тот же путь, число писем не изменилось.
- **Папки «Почты».** У каждого ящика с чтением «всё» — «Входящие»,
  «Отправленные» (без перенесённых в архив и папки), «Архив», «Спам»,
  «Корзина» (счётчик не показывается). «Все письма», «Мне назначено», «Мои
  клиенты», «Без привязки» не показывают письма с `box_state`. В списке у
  письма — метки, папка ящика, «Переносится: …», «Не перенесено» (подсказка —
  причина); в шапке письма — то же и текст ошибки.
- **Выбрать все письма папки.** Когда отмечены все показанные строки, а в
  папке их больше, панель выбора предлагает «Выбрать все письма папки: N»;
  действие уходит с `all=1` и фильтрами списка (папка, поиск,
  непрочитанные, ответственный, привязка, метка), сервер строит тот же
  запрос (`listQuery()`), не больше 5000 писем за раз.
- **Метки** — данные CRM (`cms_comm_label`, общие для сайта, цвет из
  палитры), фильтр «Метка» в списке. Где папка хранит свои ключевые слова
  (`PERMANENTFLAGS` содержит `\*`; Яндекс — да), задача пишет их как флаги
  `SkeekS_label_<id>` и снимает снятые (`labels_dirty`); с сервера метки не
  читаются. «Это спам» / «Не спам» дополнительно ставят `$Junk` /
  `$NotJunk`, где сервер это позволяет.

## Поиск по переписке

Поиск «Почты» находит переписку, в любом письме которой есть каждое слово
запроса (слова короче двух букв пропускаются, не больше пяти): отправитель,
получатели, тема и текст, у писем без текстовой части — текст из HTML
(раньше такие письма, 1119 из 1686 на стенде, не находились). Строка
поиска письма — `cms_comm_message_search` (нижний регистр, «ё» как «е»,
до 20 000 знаков текста, `utf8mb4_bin`), её пишет
`CmsCommMessage::afterSave()` для любого писателя. Запрос —
`cms_comm_conversation_id IN (переписки со словом)`; совпадения считаются
только в письмах, которые сотрудник может читать (администратору — без
проверки). План на стенде (1689 писем, 6 МБ строк поиска): подзапрос
материализуется по узкой таблице, ~30 мс; прямой перебор текстов и HTML
писем — ~190 мс. На десятках тысяч писем следующий шаг — FULLTEXT по той же
таблице.

## Спам и правила разбора

Согласовано с владельцем 23.10.2026, реализация отложена (этап 2, пункт 4).
Спама много, поэтому автоматика не должна превращать его в записи CRM.

- **Лиды из писем незнакомых отправителей автоматически не создаются.** Такие
  письма лежат в «Неразобранных», лид создаётся одним щелчком (этап 2, пункт 3).
  Иначе CRM заполняется мусором.
- **Первый фильтр — почтовый сервис.** Забираем только «Входящие» и
  «Отправленные», папку «Спам» не забираем. «Это спам» в CRM переносит
  письмо в папку спама на сервере, чтобы фильтр сервиса учился.
- **Рассылки и автоматические письма не порождают записей**: заголовки
  `List-Unsubscribe`, `Precedence: bulk/list/junk`, `Auto-Submitted` (кроме
  `no`), отправители `noreply@`/`mailer-daemon@`, домен или адрес из
  стоп-списка CRM (пополняется кнопкой «Это спам»).
- **Автоматика только при сильном сигнале**: письмо от известного клиента
  (адрес есть в CRM) может стать задачей; автоответ «задача №… принята»
  уходит только известным адресам, не на автоматические письма и не чаще раза
  в сутки на переписку. Автоответ незнакомым запрещён: он подтверждает
  спамерам живой адрес и при подделанном отправителе уходит постороннему.
- **«Лид из каждого письма»** — только настройкой отдельного ящика заявок
  (zakaz@, письма форм сайта), по умолчанию выключено.
- **ИИ (этап 8)** помечает письмо «похоже на заявку» и предлагает лид, но
  сам его не создаёт.

## Действия над сообщением

Меню у любого сообщения (письмо, бот, чат): «Создать задачу / лид / сделку»,
«Привязать», «Ответить», «Переслать». Форма создания открывается заполненной
(тема, цитата, вложения, связи переписки), после сохранения — связь «создано
из сообщения» и отметка у сообщения. Статусы задачи и ответы менеджера могут
уходить обратно в переписку («Задача №124 принята / выполнена»). В ядре для
этого — «создание из источника» (`source=model_code:id`), полезное и для
«задача из звонка», «сделка из лида».

**Сделано для писем (23.10.2026).** Ядро (`skeeks/cms`): реестр
`Skeeks::$recordSources` (тип → `source\RecordSourceInterface`: `find`,
`supports`, `prefill`, `enforce`, `created`, `describe`) и обработчики
стандартного окна создания `source\RecordSources`: окно любой модели с
`?source=<тип>:<id>` заполняется источником, над полями — строка «Из письма
«…» от …», после сохранения источник связывает запись в той же транзакции.
Почта регистрирует тип `message` (`source\MessageRecordSource`), вся работа —
в сервисе `services\MessageRecordFactory` (на него обопрутся правила части 4
и инструменты `cms-mcp`: `create($message, $type, $attributes)` создаёт и
сохраняет запись без окна):
- задача: название — тема, описание — «Письмо от …, дата» и собственный
  текст письма без цитат (`helpers\MailText`: блоки цитат почтовых программ,
  строки «> », вводные строки «…пишет:», «On … wrote:»), лид, компания или
  клиент письма, видимые сотруднику (компания или клиент лида, если у письма
  своих нет);
- лид: название «Письмо «тема»: имя, адрес», описание, источник `email`,
  название источника — наш ящик, `source_data` (id письма, Message-ID, от
  кого, тема), компания и клиент письма; после сохранения — адрес
  отправителя в email лида (если он не наш). `source_ref` не заполняется:
  какой лид создан из письма, знает связь `created`;
- сделка: название — тема, компания или клиент письма; описание сделки
  видят клиенты, поэтому текст письма в неё не попадает.
После сохранения письмо получает связь `created` с записью (отметка
«Задача №…», «Лид №…», «Сделка №…» в шапке письма и в строке списка), а
остальные письма переписки — `thread`; в ленте записи («Создано из входящего
письма») видны все письма переписки. Вверху карточки задачи, лида и сделки —
заметная строка «Создано из письма «Тема» от …, дата», тема открывает письмо
в панели (ядро: `source\RecordOriginInterface` + `RecordOriginWidget`, почта:
`MessageRecordSource::origins()`; сотруднику без доступа к письму — «из
почтового ящика, к которому у вас нет доступа», без ссылки). С 23.10.2026
(выпуск 1.2.1) там же для любой привязанной к письмам задачи,
лида или сделки — «Письмо «Тема» от …» или «Переписка последнее из N: …»
(видимые сотруднику письма, кроме того, из которого запись создана; тема
открывает письмо). Лента задачи показывает типы
`Skeeks::$activityLogTypes` (в ядре заменено `comments()` на `activity()`).
Файлы письма в запись пока не переносятся (по правилу «файл — копией», см.
реестр файлов).

## Разбор писем

`services\MessageSorting` (23.10.2026) — ручной разбор, одна операция на
действие для «Почты», будущих правил и `cms-mcp`:
- `link($message, $type, $id, $conversation)` — письмо или вся переписка к
  лиду, компании, клиенту или сделке, которую сотрудник видит
  (`services\CrmRecords::find()` — те же `forManager()`); пишет
  `MessageLinker` с типом `manual`, лента — как у автоматической привязки;
  снимает исключение;
- `unlink(...)` — удаляет связи и их записи в ленте; для всей переписки
  запоминает исключение (`cms_comm_link_exclusion`);
- `assign($message, $userId|null)` — ответственный за переписку: только
  активный сотрудник, которому письмо видно (`forManager($user)`),
  назначенному (не себе) — `CmsWebNotify` «Вас назначили ответственным за
  переписку «…»» со ссылкой на письмо (как уведомление о новом письме);
- `createdRecords()` — записи, созданные из письма, для отметок.
Видимость письма через привязку (`forManager()`, «Мои клиенты») теперь
учитывает и сделки, и задачи (`CrmRecords::types()`); для этого в ядре
`CmsTaskQuery`/`CmsDealQuery::forManager($user)` передают сотрудника во
вложенные условия. Метки CRM показываются только видимые сотруднику
(`CrmRecords::isVisible()`).

Интерфейс: в панели письма «Привязать» (окно `link`, клавиша l), «Создать ▾»
(только разрешённые сотруднику окна создания), «Ответственный ▾» (список
`assign` GET, выбор POST), строка «Ответственный: …», «×» у записи
(«Только это письмо» / «Всю переписку»); после действия письмо и список
обновляются сразу. В списке — меню строки (правая кнопка мыши или «⋮»):
открыть, прочитано/не прочитано, привязать, создать задачу/лид/сделку,
назначить меня; фильтры «Ответственный» (все, я, без ответственного,
другие ответственные видимых переписок) и «Привязка» (`assignee`, `linked`
в адресе списка и «Показать ещё»); папка «Мне назначено» (`assigned`).
С 23.10.2026 «Ответственный» и фильтр «Привязка» по умолчанию скрыты, см.
«Почта: решения».
Панель письма открывается с `updateSuccessCallback`: сохранённая из письма
запись помечает панель изменённой, и стандартная реакция при её закрытии
перезагрузила бы всю страницу — вместо этого обновляется только список.

## ИИ

ИИ — пользователь CRM со своей ролью, инструменты — те же `cms-mcp`. Уровни
самостоятельности для бота, переписки и вида действия: выключен,
подсказывает (черновик на подтверждение), действует и сообщает, полностью сам
(цены, сроки, деньги — никогда сам). Если менеджер взял диалог или ответил —
ИИ молчит. Сценарий группового чата: клиент пишет «поправить баннер» → разбор
переписки (с паузой, чтобы собрать сообщения) → проверка открытых задач
компании → задача → ответ в чат → по выполнении правило пишет в чат. Журнал
решений `cms_ai_run` с отметками «верно/неверно». Сообщения клиента — данные,
а не команды: права инструментов ограничены привязанной компанией и этой
перепиской; лимиты. Модель выбирается на уровне сайта (152-ФЗ: российская или
зарубежная). Пакет `cms-ai`.

### ИИ: разбор базы и личные предложения

Согласовано с владельцем 24.10.2026. Задача: пройти базу компаний, клиентов
и лидов вместе с историей общения, понять, кому что предложить (бывшие
клиенты, устаревшие сайты, сферы с готовыми решениями — например
`/solutions/plitka`, остывшие лиды), и писать людям индивидуально, прикладывая
предложение. Все бизнес-процессы — личная ссылка, «открыто» в ленте, задача
«Позвонить», отписка, отчёт — работают так же, как у менеджера.

**Где живут инструменты.** `cms-mcp` только подключает провайдеры
инструментов (`McpComponent::$providers`, `McpToolProviderInterface`);
инструменты почты, рассылок и согласий — в `cms-communication`, предложений —
в `cms-proposal`, каждый пакет регистрирует свой провайдер, если `cms-mcp`
установлен. Права — через OAuth-пользователя и `forManager()`, как в
интерфейсе.

**ИИ-1. Чтение** (`cms.communication.read` и аналоги):
- история клиента одним списком для лида, компании, клиента: звонки, письма,
  комментарии, задачи, сделки, счета, отправки предложений и их открытия
  (существующий `cms_company_timeline_get` писем и предложений не показывает);
- письма и переписки клиента с текстом без цитат и подписей, без вложений;
- предложения: список и карточка, готовые общие Презентации, КП;
- «можно ли писать»: `MailingPolicy` (отписки, стоп-лист, согласие по теме).

Как сделано (24.10.2026):
- **Общий инструмент истории, а не расширение `cms_company_timeline_get`.**
  Тот — журнал изменений компании и её записей (вставки, правки) и есть только
  у компании. История ИИ-1 — `cms_crm_history_get` в `cms-mcp` для лида,
  компании и клиента: лента карточки (`CmsLogQuery::activity()`, ровно её
  записи — тест сверяет с реальными карточками) плюс записи блоков карточки
  (задачи, сделки, счета, платежи) плюс события пакетов (отписки и согласия).
  Пакет, владеющий типом ленты, сам описывает его запись
  (`HistoryLogDescriberInterface`) с тем же правилом доступа, что у рендерера
  ленты: письмо чужого ящика — `access: false` без содержания.
- **Обзор клиента** — `cms_crm_client_overview_get` и `_list` в `cms-mcp`:
  сфера — категории компании; последний контакт — звонок, письмо или СМС
  записи и её лидов; сотрудничество — сделки, оплаченные счета и поступления,
  `state: active|former|none` и `ended_at`. Разделы `proposals` и `mailing`
  добавляют пакеты (`OverviewContributorInterface`).
- **Точка расширения `cms-mcp` общая**: пакеты регистрируют провайдеры,
  описатели, источники и разделы в `params['cmsMcp']` своего конфига; без
  `cms-mcp` это ничего не делает (блок компонента `cmsMcp` без `class` сломал
  бы такие сайты).
- **Права и scope прежние**: `cms.activity.read` (история),
  `cms.company.read` (обзор), `cms.communication.read` (почта, рассылки,
  предложения) — повторная авторизация клиентов не нужна; видимость —
  `forManager()` OAuth-сотрудника.
- **Персональные данные**: адреса и телефоны замаскированы
  (`i***@domain.ru`, `***-**-67`, `[телефон]` в текстах), полностью — только с
  `include_contacts=true`. Личные ссылки клиента (`/~kp/`, `/~unsub/`) не
  выдаются никогда, даже с этим флагом: их открытие засчиталось бы как
  открытие или отписка клиента.

**ИИ-2. Действия** — только с `confirm=true`, тем же путём, что у менеджера:
- черновик письма в ящике ответственного с приложенным предложением (личная
  ссылка создаётся при отправке); менеджер правит и отправляет сам — режим
  по умолчанию;
- кампания 4B с личным текстом каждого получателя: ИИ заполняет получателей
  и тексты, менеджер просматривает и запускает; дальше — ограничение
  скорости, отписка, отчёт, задача при открытии;

## Метки и учёт переходов по ссылкам из писем

Согласовано с владельцем 24.10.2026 (шаг F).

- **«Открыто» пикселем не считаем**: ложные открытия (предзагрузка картинок
  Apple Mail и прокси Gmail, Яндекса, Mail.ru), пропуски (картинки
  выключены, в том числе в нашей «Почте»), вред доставляемости личных писем.
  Надёжный сигнал — переход по ссылке.
- **В момент отправки** любого письма из CRM (личное, ответ, «Отправить
  клиенту», кампания, черновик ИИ после отправки) к ссылкам на наши домены
  (список настраивается: skeeks.com, skeeks-platform.ru …) добавляются
  `utm_source=crm`, `utm_medium=<канал: email, позже sms/max/telegram>`,
  `utm_campaign=<номер кампании | номер предложения | personal>` и личный
  код получателя `sx=<код>`. Пример: менеджер пишет
  `https://skeeks.com/solutions/plitka`, уходит
  `https://skeeks.com/solutions/plitka?utm_source=crm&utm_medium=email&utm_campaign=personal&sx=abc123`.
  Метки, поставленные менеджером, не затираются, добавляются только
  недостающие. Ссылки на чужие сайты не меняются, перенаправлений нет —
  ссылка ведёт прямо на страницу. Сохранённая копия письма в CRM и
  «Отправленных» хранит то, что ушло; в редакторе менеджер видит исходную
  ссылку.
- **Личный код** — на получателя и письмо (как отправка предложения): по
  нему переход связывается с письмом, лидом/компанией/клиентом, кампанией.
  Предложения (страница КП, переход Презентации) продолжают работать как
  есть; их метки — те же `utm_*`.
- **Учёт на наших сайтах**: небольшой скрипт засчитывает переход тем же
  честным способом, что страница КП (сигнал после показа страницы, роботы и
  проверки ссылок не засчитываются и помечаются), запоминает код на время
  визита (cookie), убирает `sx` из адресной строки (пересланная коллеге
  ссылка не записывается на получателя), записывает последующие страницы
  визита. Метрика читает `utm_*` как обычно. Для сайта не на той же
  установке, что CRM, — приём сигнала на сайте CRM по разрешённому списку
  доменов.
- **В CRM**: запись в ленте «перешёл на сайт из письма от <дата>: <страница>,
  затем …», уведомление ответственному, задача «Позвонить» — по настройке
  (правило этапа 3); в отчёте кампании — «перешёл на сайт».
- **Задел**: кнопка «Связаться с менеджером» на наших страницах для пришедших
  по коду (обращение сразу к нужному лиду) — следующий шаг после F.
- **Cookie и 152-ФЗ**: на сайтах, где стоит скрипт, нужно уведомление о
  cookie.

## Сделка как услуга: ресурсы, доступ клиента и уведомления

Согласовано с владельцем 26.10.2026. Основа этапов 6 (кабинет) и 7
(уведомления клиентам). Повод: задачи продвижения сейчас ставятся в проект
компании, а люди клиента видят их через участников проекта
(`CmsProject2user`) — это обходной путь; нужна универсальная модель прав и
уведомлений по услуге.

**Что уже есть.** Сделка — услуга: регулярные сделки, тип сделки
(`CmsDealType`), ресурсы хостинга (сайт, VPS, SSL — `cms_deal_id` в
таблицах `cms-hosting`) привязаны к сделке. Люди компании `CmsCompany2user`
с `is_root` («главный») и `is_notify`. Задачи — `cms_company_id`,
`cms_project_id`. Каналы связи — почта, СМС, боты MAX и Telegram, привязка
чата к компании, согласие и отписка у контакта (этапы 1–5).

**Сделка и ресурсы.**
- Сделка — коммерческая единица: что клиент купил одним пакетом, за что
  платит одним счётом с одним периодом, кто у нас отвечает, кто со стороны
  клиента имеет доступ. Ресурс — технический объект услуги: сайт,
  DNS-зона, SSL-сертификат, почтовый домен, VPS.
- Ресурс принадлежит ровно одной сделке и может быть перенесён в другую
  (DNS бонусом к сайту → позже отдельная сделка) с сохранением истории.
- Права и уведомления — на уровне сделки: событие ресурса («SSL истекает»,
  «сайт недоступен») поднимается до его сделки. Отдельных прав на ресурс нет.
- Тип сделки задаёт допустимые ресурсы и разделы, которые можно открыть
  клиенту.
- **Отдельная сделка**, если отличается хоть одно: деньги (цена, период,
  отдельный счёт), команда у нас (ответственный, отдел), люди клиента с
  доступом, срок жизни (разовая работа против регулярной). Иначе — одна
  сделка. Пример: «Сайт и хостинг» (сайт, DNS бонусом, позже почта) — одна
  сделка; «Продвижение» — отдельная; разовая «Доработка сайта» — отдельная.
- **Состав сделки** — список «что входит» с ценой и периодом по строкам
  (бонус — строка с нулевой ценой, видна клиенту как подарок), строка
  ссылается на ресурс, если он есть. Принятое КП превращается в сделку с этим
  составом (связь с этапом 3, шаг D).

**Задачи в сделке.** У задачи — ссылка на сделку и, при желании, на ресурс.
Задачи услуги живут в сделке; проекты остаются для внутренней работы;
существующие проекты продвижения переносятся в сделки (шаг У2).

**Что услуга открывает клиенту — настройки сделки.** Разделы (набор задаёт
тип сделки, сделка включает): задачи (смотреть / комментировать / ставить),
отчёты (например позиции и трафик продвижения), документы, счета и оплата,
управление услугой (DNS, перезапуск VPS, продление), чат по услуге.

**Права человека клиента** — два уровня, итог пересекается с тем, что открыто
в сделке:
- в компании — роль: «полный доступ ко всем услугам» (нынешний `is_root`,
  например директор) или «только выбранные услуги»;
- в сделке — участник с правами по разделам.

Готовые роли (правятся по человеку):

| Роль | Задачи | Отчёты | Документы | Счета и оплата | Управление |
|---|---|---|---|---|---|
| Директор | ✓ | ✓ | ✓ | ✓ | ✓ |
| Бухгалтер | — | — | ✓ | ✓ | — |
| Маркетолог / менеджер | ✓ | ✓ | — | — | — |
| Только просмотр | смотреть | ✓ | — | — | — |

Пример: менеджер клиента с ролью «Маркетолог» в сделке «Продвижение» видит
отчёты и участвует в задачах, документов и платежей не видит.

**Единая проверка прав** — одна служба ядра, её используют кабинет (этап 6),
бот, уведомления (этап 7), API и ИИ.

**Уведомления по сделке.**
- Пакеты регистрируют виды событий («счёт выставлен», «скоро оплата»,
  «услуга заканчивается», «задача ждёт ответа клиента», «задача выполнена»,
  «отчёт готов», «сайт недоступен»); у вида — нужное право (о счёте узнают
  только те, кому открыта оплата) и важность.
- Подписка по умолчанию — от роли (бухгалтеру — счета, маркетологу — задачи
  и отчёты, директору — важное), в сделке правится по человеку.
- Служебные уведомления не отписываются (см. «Служебные и рекламные
  сообщения»); клиент выбирает только каналы.
- Доставка: порядок каналов человека (например мессенджер → почта), запасной
  канал при недоставке, тихие часы; критичные события («сайт упал») — без
  тихих часов. Рабочий групповой чат компании или сделки — тоже получатель.

**Правила, закреплённые после ревью У1–У2 (26.10.2026).**
- Перенос ресурса в другую сделку: задачи и строки состава ресурса остаются в
  прежней сделке как её история (привязка к ресурсу сохраняется), новые
  привязки — только в пределах сделки ресурса; обе ленты пишут, что осталось.
  Кнопка переноса в интерфейсе — шаг У3, по этому правилу.
- Новая область доступа пакета закрыта, пока тип сделки не разрешил её явно;
  без настроек типа открыты только пять основных областей.
- **Оплата и выполнение — разные состояния услуги.** «Оплачено» (счета и
  период сделки) отдельно от хода работ: «выполняется», «приостановлено»,
  «завершено» (например, анализ оплачен, но ещё не готов). Сейчас у сделки есть
  только активность и срок; состояние выполнения вводить вместе с кабинетом и
  уведомлениями (У4–У5), не в У1–У2.
- **Один договор подключения услуги.** Пакет новой услуги регистрирует в одном
  месте: ресурсы (поставщик ресурсов — уже есть), свои области доступа (есть),
  действия клиента в кабинете, виды событий (У4) и реакции на оплату и конец
  периода. Общий механизм даёт права, счета, напоминания и доставку
  уведомлений — новая услуга подключается без повторной обвязки. Описать
  договор при проектировании У4 и подключить по нему хостинг первым.

**«С кем какая у нас связь»** — карточка человека клиента показывает его
каналы и их состояние: email (подтверждён, недоставки, отписка от рекламы),
телефон для СМС, личный чат MAX/Telegram (привязан, последнее сообщение),
мобильное приложение, последний успешный способ доставки.

**Варианты по умолчанию** (вопросы владельцу, ответы по умолчанию приняты):
1. Одна сделка — коммерческий пакет услуг (правила «отдельной сделки» выше),
   не одна сделка на каждый ресурс.
2. Человек клиента без входа в кабинет допустим: контакты и подписки есть,
   пароля нет (например бухгалтер получает счета на почту).
3. Директор клиента сам выдаёт доступы своим людям в кабинете — в пределах
   своих прав (шаг У5).
4. Клиент ставит задачи по услуге, если в сделке открыто «ставить задачи».

## Единый механизм уведомлений (сотрудники и клиенты)

Согласовано с владельцем 26.10.2026 (шаг У4, этап 7). Уведомления
сотрудникам и клиентам — один механизм: событие, получатель, его каналы и
настройки; различается только вид получателя. Повод: у сотрудников всё больше
видов уведомлений в окне колокольчика, они не разделены, одно событие
приходит дважды («клиент открыл презентацию» и «поставлена задача
„Позвонить“»), нельзя удалить одно уведомление, нельзя получать уведомления
в мессенджер.

- **Реестр видов событий** от пакетов: код, название, категория
  (задачи; клиенты и предложения; почта и чаты; счета и платежи; система),
  важность (обычное, важное, срочное), для клиентов — нужное право сделки.
- **Окно уведомлений**: разделы по категориям; связанные события
  склеиваются в одно («Плитка Для Вас Москва открыла презентацию —
  поставлена задача „Позвонить“»); действия у уведомления — удалить одно,
  прочитано, «не уведомлять о таком»; «Очистить» — для всех.
- **Каналы получателя**: CRM (колокольчик), почта, MAX и Telegram (личный
  диалог с ботом по одноразовой ссылке — тот же механизм привязки
  собеседника, что для клиентов в шаге 5.4), мобильное приложение (push),
  для клиентов ещё СМС и рабочий групповой чат сделки.
- **Настройка «что и куда»**: строки — категории, столбцы — каналы, галочки;
  готовые варианты в один щелчок («Всё только в CRM», «Важное в MAX,
  остальное в CRM», «Важное в Telegram, остальное в CRM»); тихие часы;
  срочное приходит всегда.
  Сотрудник настраивает в профиле, клиент — в кабинете (У5) тем же блоком.
- **Доставка**: порядок каналов, запасной канал при недоставке, без дублей
  (одно событие — одно сообщение в канале), журнал доставки.
- **Служебные уведомления клиентам не отписываются** (см. «Служебные и
  рекламные сообщения»), клиент выбирает только каналы; получатели — по
  правам сделки (У1) и подпискам по ролям.
- Позже (этап 8): сводка за день от ИИ.

Порядок: У4a — сотрудники (проверяем на себе), У4b — клиенты, У5 — кабинет.

## Сущности CRM: сделки, заказы, услуги и обслуживание

Согласовано с владельцем 27.10.2026. **Целевая модель и план перехода;
реализация этого перехода не начата, кроме переименования интерфейса
(27.10.2026, см. словарь в начале файла и П6).** Этот раздел заменяет решение от
26.10.2026 «лид — только новый клиент» и прежние правила импорта холодной
базы в лиды. Уникальность клиента сохраняется, самостоятельные продажи ему
могут повторяться. Исторические разделы выше описывают код под прежними
названиями: «лид» означает `CmsLead`, «сделка» — `CmsDeal`. Не считать их
переименованными или мигрированными только из-за изменения этого плана.

### Сущности и названия

| Название в целевом интерфейсе | Существующая основа | Ответственность |
|---|---|---|
| Клиенты: компании и люди | `CmsCompany`, `CmsUser`, связи людей с компанией | Кто покупает; контакты и общая история отношений |
| Сделки | Нынешние лиды, `CmsLead` | Самостоятельная возможность продажи: потребность, источник, ответственный, воронка, предложения, результат |
| Заказы | `cms-shop`: `ShopOrder`, `ShopOrderItem` | Конкретный состав покупки, количества, цены, доставка и исполнение заказа |
| Услуги и обслуживание | Нынешние сделки, `CmsDeal` | Разовая работа или регулярное обслуживание: условия, задачи, ресурсы, клиентские доступы, сроки и продление |
| Счета, платежи, документы | Существующие сущности `cms-shop` | Общая финансовая часть для заказов и услуг |

Подписка — регулярная разновидность услуги, а не общее название `CmsDeal`.
Разработка сайта — разовая услуга, хостинг — регулярная. Каталожная позиция
«Хостинг» описывает предложение; услуга конкретного клиента хранит его
условия, ресурсы и срок обслуживания. Это разные назначения данных.

Не создавать второй заказ для CRM и отдельные счета или платежи для услуг.
Уже сейчас `ShopOrder` связан со счетами и платежами, а `CmsDeal::createBill()`
создаёт `ShopBill` без обязательного заказа. Новые связи продажных сделок с
заказами и услугами ещё предстоит реализовать. Наличие связи с оплатой само
по себе не означает готового распределения денег между несколькими услугами.

Сделка может привести к одному или нескольким заказам/услугам либо изменению
существующей услуги. Сохранять саму сделку и её историю переговоров; не
подменять её карточкой исполнения. Не заставлять каждый сценарий проходить
все сущности: покупка через магазин может сразу создать заказ, индивидуальная
услуга — выставить счёт напрямую, обычное продление — создать очередной счёт
без новой сделки и заказа. Связи и их ограничения уточнить до миграции.

правка документа не меняет код и не подтверждает готовность автоматизации.

Обращение — исходная заявка с сайта, звонок, письмо или сообщение клиента.
Разбор — определение клиента, смысла обращения и места дальнейшей работы.
Это входное событие и действие над ним, а не две новые обязательные сущности
CRM. Отдельная карточка «Лид» перед каждой продажной сделкой не вводится.
Исходное обращение, его источник и история сохраняются.

**Уже реализованная основа разбора — «Новые».** Проверено по текущему коду
27.10.2026: `CmsLead::STATUS_NEW` и колонка «Новые» в
`CmsLeadBoardService` служат очередью ещё не взятых в работу продажных
обращений. Это наш функциональный аналог неразобранных сделок, а не новая
сущность, которую нужно создавать при переходе.

У новой записи без ответственного доступно «Взять в работу»:
`AdminCmsLeadController::claim()` назначает текущего сотрудника исполнителем
и переводит ту же запись в `STATUS_IN_WORK`. Перенос из «Новых» в рабочий
этап канбана также назначает исполнителя, если он ещё не назначен, и меняет
статус. ID и история карточки сохраняются; второй сделки при этом не возникает.
Доступ к очереди ограничен правами, а конкурентное изменение записи
обрабатывается через optimistic lock. Это проверка исходного кода, не новый
прогон на стенде.

```text
Новое продажное обращение → Сделка «Новая» (ещё не разобрана)
                         → «Взять в работу» / рабочий этап канбана
                         → Та же сделка «В работе» с ответственным
```

Разбор не следует изображать как обязательный отдельный объект перед
созданием сделки: для такого входящего запроса он уже начинается в «Новых».
При явном назначении ответственного запись может сразу поступить в работу.
Будущий общий разбор каналов должен переиспользовать этот механизм и
дополнить маршрутизацию продолжений и поддержки, описанную ниже; наличие
статуса «Новый» само по себе не подтверждает готовность всей маршрутизации.

```text
Обращение → Разбор
               ├─ Новая потребность → Новая сделка → Заказ и/или услуга
               ├─ Продолжение переговоров → Существующая сделка
               └─ Поддержка → Задача по действующей услуге
```

- **Новая потребность — новая сделка.** Найти или уточнить клиента и проверить
  повтор самого запроса. Самостоятельная новая потребность существующей
  компании создаёт новую продажу с той же компанией, без дублирования клиента.
- **Продолжение — в существующую сделку.** Уточнения, ответы и материалы по
  тому же обсуждению дополняют его историю. Несколько обращений могут относиться
  к одной сделке; каждое письмо не становится новой продажей.
- **Поддержка — в задачу по услуге.** Обращение по исполнению или обслуживанию
  связывается с соответствующей услугой и создаёт задачу; продолжение уже
  существующей задачи дополняет её, не создавая дубль. Если услуга или задача
  неоднозначна, сначала уточнить связь. Запрос дополнительной платной работы
  с новой потребностью может быть направлен в новую сделку.

Разбор выполняет сотрудник либо автоматизация по проверяемым правилам.
Неоднозначные случаи остаются на ручной разбор; спам и автоответы не создают
продажи. Привязка к компании, сделке или услуге не расширяет права сотрудника.
Повторная доставка одного события не создаёт вторую сделку или задачу.

Для пользователя сохраняется привычный процесс CRM: получить обращение,
разобраться в потребности, работать с клиентом, задачами и сделкой в воронке.
После продажи исполнение продолжается в заказе и/или услуге. Холодная строка
импорта и просмотр презентации сами по себе не являются обращением с новой
потребностью; для них действуют отдельные правила аудитории и сигналов интереса.

### Два сценария

**Плитка, резка и доставка.** Сделка — подбор и согласование. Заказ магазина —
плитка и резка в составе покупки, доставка через существующий механизм заказа.
Резка обычно является работой по строке заказа с отдельным заданием исполнения
(размеры, материалы, количество, готовность), а не самостоятельной подпиской
или карточкой обслуживания. Счета и платежи относятся к заказу. Не начислять
доставку одновременно строкой и через `delivery_amount`. Обработка работ без
складского остатка, резерва и физического веса и производственное задание —
предстоящая интеграция; обычная строка заказа не доказывает её готовность.

**Сайт и хостинг.** Сделка — согласование разработки и обслуживания.
«Разработка сайта» — разовая услуга с задачами и приёмкой; «Хостинг» —
регулярная услуга с тарифом, сроком и ресурсами. Заказ необязателен для
индивидуальной разработки. При покупке готового пакета через магазин его
заказ подключает соответствующие услуги; заказ завершается, хостинг продолжает
работать. Первый оплаченный в заказе период не начисляется услугой повторно.

### Воронки продаж

Воронка принадлежит продажной сделке (нынешнему `CmsLead`), а не заказу или
обслуживанию. Можно настроить несколько воронок с собственными этапами.
Примеры, а не обязательные одинаковые этапы для всех установок:

| Продажа плитки | Разработка сайта |
|---|---|
| Новое обращение | Новое обращение |
| Подбор товара | Выяснение требований |
| Расчёт стоимости | Подготовка предложения |
| Предложение отправлено | Предложение отправлено |
| Согласование | Согласование |
| Успешно / отказ | Успешно / отказ |

- Одна сделка — одна самостоятельная попытка продажи. Несколько потребностей
  одной компании могут находиться в работе одновременно. Повторные письма,
  звонки и формы по тому же открытому обсуждению добавляются в него.
- Для каждой воронки определить критерий успеха: например подтверждённый заказ
  или предоплата. Черновик заказа, отправка КП и открытие ссылки сами по себе
  не завершают продажу успешно.
- Хранить историю переходов: прежний и новый этап, время, исполнитель,
  воронка; фиксировать результат, причину отказа, источник и даты открытия/
  закрытия. Перенос между воронками и переоткрытие также сохраняют историю.
- Отчёты разделяют первые и повторные продажи, источники, ответственных,
  конверсию и время на этапах. Правила периода и учёта переоткрытий должны быть
  явными; текущая колонка канбана не заменяет историю конверсий.
- Согласованная сумма сделки, сумма заказа, выставленные счета и поступившие
  платежи — разные показатели. Несколько счетов не умножают число продаж;
  связанные суммы не складываются повторно как независимая выручка.
- Разовую стоимость и регулярную стоимость с периодом показывать отдельно.
  Годовую оценку регулярного дохода считать только по явно заданной методике.
- Обычные регулярные начисления не создают сделки. Продажа дополнительной
  услуги, нового тарифа или обсуждение новых условий может создать сделку.
- Комплектация, резка, доставка, разработка и приёмка — исполнение, а не этапы
  продаж. Оплата и выполнение имеют отдельные состояния; «оплачено» не равно
  «выполнено», успешная продажа не означает завершения обслуживания.

   API-контракты; возможные новые имена API вводить отдельно с совместимостью.

с исполнением, П5 доводит источники обращений и коммуникации, П6 завершает
переход. Это не автоматическое продолжение выпуска У1–У2. Проектный модуль
продвижения менять только после его коммита по отдельному плану.

Критерии приёмки: повторная продажа не дублирует клиента; обе сценарные цепочки
работают; повтор события не создаёт второе начисление; ограниченный менеджер
не получает чужие контакты/финансы; старые заказы, услуги, оплаты, ссылки и
интеграции сохраняются; конверсия и суммы не удваиваются; регулярное
обслуживание продолжается после закрытия продажной сделки и заказа.

### Договор связей (П1 выполнен, согласовано с владельцем 27.10.2026)

Инвентаризация П1 — только чтение, без изменений кода и данных. Факты боевого
skeeks.com на 27.10.2026:
- прямой связи сделка → заказ → услуга нет; общие у них только компания,
  задачи (`cms_task.cms_lead_id`/`cms_deal_id`) и КП;
- из 238 сделок (`CmsLead`) около 180 — ручной холодный обзвон по базам
  поставщиков, у 221 нет компании, успешных 3;
- заказов магазина 0, счетов 5238, платежей 9554; 864 счёта привязаны к
  нескольким услугам, 996 платежей — к нескольким услугам, 203 — к нескольким
  счетам, суммы распределения нигде не хранятся;
- автоматических начислений нет: счета выставляют люди,
  `CmsDeal::createBill()` не вызывается, оплата не продлевает услугу.

Решения:
1. **Связи.** Клиент 1—* сделка. Сделка 1—* заказ: nullable
   `shop_order.cms_lead_id` и `shop_order.cms_company_id`, у заказа не больше
   одной исходной сделки. Сделка → услуга — таблица происхождения в ядре
   (`cms_deal_id`, `cms_lead_id`, вид: подключение / изменение условий / новые
   условия продления, `shop_order_item_id` nullable), уникальность защищает от
   повторной обработки строки заказа. Одна колонка `cms_lead_id` в услуге не
   годится — теряется история.
2. **Успех сделки ничего не создаёт сам.** Заказ и услуга оформляются кнопкой
   («Оформить заказ», «Подключить услугу»). Переоткрытие и повторный успех не
   создают новых записей и второго партнёрского вознаграждения.
3. **Критерий успеха** — настройка воронки: вручную, подтверждённый заказ или
   первая оплата. Автоматический критерий только предлагает закрыть сделку,
   закрывает человек.
4. **Один владелец начисления** за каждую работу и период: строка заказа или
   счёт услуги. У связи счёта с услугой — `period_from`/`period_to`
   (nullable для старых записей), уникальность «услуга + начало периода» среди
   неотменённых счетов. Период, оплаченный заказом, отмечается в услуге.
5. **Продление** — одна служба ядра «оплачен счёт за период → новый срок»,
   идемпотентная по счёту; заказы, ручное «оплачено» и API вызывают её. Ручная
   правка срока — только администратор, с записью в ленте.
6. **Распределение платежа (П4б).** Один платёж на несколько счетов и один счёт
   на несколько услуг — нормальная практика (клиенту выставили два счёта, он
   оплатил одним платежом); не запрещать, а хранить суммы: `amount` в
   `shop_bill2payment`, затем в связях услуг со счетами и платежами.
   Автоматическая разноска: платёж равен сумме счетов — каждый счёт закрывается
   своей суммой; меньше — сначала старые счета, остаток частичной оплатой;
   больше — остаток авансом клиента к следующему счёту. Счёт делится между
   услугами по своим строкам. Бухгалтер может поправить суммы вручную. Пустая
   сумма у старых записей означает «весь платёж, как раньше», историю не
   пересчитывать.
7. **Защита от повторов** — ключ события у операций «создать заказ из
   сделки», «подключить услугу по строке заказа», «выставить счёт за период».
8. **Воронки по умолчанию** — «Входящие» и «Исходящие продажи». Холодные
   сделки из баз поставщиков мигрируют в «Исходящие». «Неразобранное» —
   нынешний статус «Новый» с действиями «объединить», «в поддержку», «спам».
9. **Работа менеджера.** Конкретный потенциальный клиент — сделка, в форме
   которой компания и контакт находятся или создаются, с проверкой повторов по
   всей базе (ответ «клиент уже есть, ответственный …» без чужих контактов).
   Массовая холодная база — компании и контакты в аудитории или списке, без
   сделок. Входящая заявка — сделка в «Неразобранном». Контакты, введённые в
   сделке, остаются у неё как «Из обращения» и переносятся в карточку клиента по
   выбору, без массового переноса задним числом.
10. **Поручение сделки** без всей компании: поручённый видит компанию только
    как «название + ответственный». Права сотрудников — одна служба ядра
    (условно `CrmAccess`), как `DealAccess` для клиентов.

Отложено: где проверять сценарий «плитка» (на skeeks.com заказов нет; нужен
клиентский сайт с магазином) — решить до П3. Попутные ошибки `cms-shop` из
инвентаризации — отдельной задачей.

Порядок и оценка: П2а — «Неразобранное», поиск повторов и назначение
(3–4 дня, можно выпускать сразу); П2б — воронки, этапы, история переходов,
отчёт, миграция (5–7); П2в — инструменты `cms_lead_*` в API (1–2, сразу);
П3 — заказ в CRM (5–7); П4 — происхождение услуги, период счёта, служба
продления, выполнение (7–10); П4б — суммы распределения платежей (3–4);
П5 — импорт в двух режимах, аудитория, служба прав сотрудников (7–10);
П6 — отчёты, раздел «Заказы», миграция данных, выпуск (3–5). Всего ≈ 35–50
рабочих дней. П3 и П4 начинать только по утверждённым правилам денег (пп. 4–6).
Полный документ инвентаризации — заметки сессии П1 (`crm-entities-p1.md`).

### Правило «базового сайта» (согласовано с владельцем 27.10.2026)

Ядро `skeeks/cms` стоит на всех сайтах, `cms-communication` и прочие пакеты
CRM — только там, где нужны. Каждый шаг П2–П6 (и любая доработка CRM в ядре)
принимается только после проверки на обычном клиентском сайте без
`cms-communication` и без настроенной CRM:
- **заявки с форм** (`cms-module-form2`) приходят и видны как раньше: на сайте
  без менеджеров и ответственных они не теряются в разборе, видимом только
  администратору, и не требуют новых действий;
- **меню** не показывает CRM-разделы, которыми сайт не пользуется (группа
  «Услуги», «Услуги клиентов», «Сделки» и т.п. — по праву или настройке, решение
  — отдельная сессия);
- **работа без пакетов CRM**: ядро не ссылается на классы `cms-communication`,
  `cms-proposal`, `cms-hosting`; их точки срабатывают только через события и
  регистрацию самих пакетов;
- **миграции ядра** только добавляют пустые поля и таблицы и не меняют поведение
  существующих данных; обновление ядра на клиентском сайте = обычная выкладка с
  миграцией.

### Рассылки в новой модели (согласовано с владельцем 27.10.2026)

Сделки заранее не создаются: ни на импортированную базу, ни на получателей
кампании. Письмо и Презентация привязаны к компании или контакту, сделка
появляется из конкретного интереса.

1. **Аудитория — список рассылки** (этап 4D). Наполнение (способы можно
   смешивать):
   - импорт файла: каждая строка — через общий поиск повторов (`CrmMatcher`,
     П2а); найдена компания или контакт — берётся она, иначе создаётся
     компания и контакт с источником «Рассылка: база …» и состоянием «холодный,
     согласия нет»; действующие клиенты, недавние отказы и отписки
     отсеиваются; сделок нет;
   - выбор из разделов CRM и правила с автопополнением (уже есть);
   - «Добавить адреса»: на каждый адрес тихо создаётся карточка контакта (при
     необходимости — компании). Голые адреса в списке не хранятся: согласие,
     отписка и ответ должны принадлежать контакту.
2. **Кампания по списку** (этап 4B): тема, ящик менеджера или отдельный домен
   для холодных писем, личная Презентация каждому, исключающие списки, «одна
   компания — одно письмо». Отправка пишется в ленту компании/контакта.
3. **Реакции:**

| Реакция | Что происходит |
|---|---|
| Открытие письма | Отметка в отчёте кампании |
| Переход по ссылке, просмотр Презентации | Сигнал «тёплый» в карточке и отчёте; по настройке кампании — задача ответственному «Позвонить: смотрел Презентацию». Сделки нет |
| Ответ на письмо, «Связаться», заявка | Сделка в «Неразобранном» с источником «Рассылка: <кампания>» и историей отправки (письмо и Презентация); повтор — по `source_type` + `source_ref`, открытая сделка по той же потребности дополняется |
| Отписка | Отметка у контакта по теме, следующие списки его пропускают |

Менеджер может сам создать сделку тёплому получателю из карточки компании.
Возможная настройка кампании на будущее: «создавать сделку при просмотре
Презентации» (по умолчанию — только при ответе).

Работы:
- П2а — точка «ответ на рассылку → сделка в „Неразобранном“ с историей
  отправки» вместо нынешней задачи «Ответить: … ответил на рассылку»;
- П5 — импорт в список через поиск повторов (вместо создания лидов),
  «Добавить адреса», задача по сигналу «тёплый», перевод старых участников
  списков с `lead` на компании и контакты.

**Предлагаемый договор связей для реализации после П1.**

- Продажа имеет одного основного клиента (компанию или человека); контактное
  лицо компании не становится отдельным покупателем. Сохраняются исходные
  контакты обращения, связь с клиентом не перезаписывает их молча.
- Одна продажа может создать несколько заказов. У заказа — не более одной
  исходной продажи; заказ из магазина может не иметь её. Для первой версии
  не вводить объединение нескольких независимых продаж в один заказ.
- Одна продажа может подключить несколько услуг. У услуги одна исходная
  продажа, но последующие продажи могут менять её условия. Для этих изменений
  нужна история связей с назначением «подключение / изменение условий»,
  временем и автором; один перезаписываемый `lead_id` эту историю не заменяет.
- Заказ связывать с подключённой услугой на уровне позиции и оплаченного
  периода/работы. Повторная обработка той же позиции не подключает услугу
  второй раз. Заказ на новый период существующей услуги не создаёт её копию.
- За каждую работу/период начисляет один источник: заказ либо услуга.
  Сумма связи платежа с услугой не считается автоматически равной всему
  платежу. До объединённой оплаты нескольких услуг описать распределение,
  частичную оплату, возврат и отмену; имеющиеся map-таблицы этого не решают.
- Заказы, счета и оплаты живут в `cms-shop`; в ядре — продажи, клиенты,
  услуги и права. Интеграцию заказов поставляет магазин, аудиторию и рассылки —
  коммуникации. Новая логика ядра не должна требовать установленного модуля
  рассылок или конкретного отраслевого пакета.

**Импорт: два явно выбранных режима.** Предлагаемое поведение, не описание
готового импорта. Режим выбирают до сопоставления колонок и показывают в итогах.

| Режим | Что означает строка | Результат |
|---|---|---|
| База для рассылки | Потенциальный адресат, интерес ещё неизвестен | Компания/контакт и участие в аудитории; ни сделки, ни автоматической задачи на каждую строку |
| Заявки / сделки | Конкретная потребность или уже начатая работа продавца | Новая продажа либо дополнение той же открытой; найденный клиент переиспользуется |

Для холодной базы использовать существующие компании/людей и списки
получателей. `CmsCommContact` остаётся адресом канала с согласиями, не новой
карточкой человека. Неизвестный email не доказывает существование отдельного
человека или компании: сохранить такую строку в области разбора импорта до
уточнения; не создавать фиктивную компанию по домену. Возможность отправки
неразобранным строкам не включать в первый выпуск. Перед реализацией проверить,
что создание контактной карточки не выдаёт учётную запись/приглашение в кабинет.
Не хранить постоянную аудиторию только в строках файла: после разбора она
должна переживать архивирование импорта и поддерживать общие правила списков.

**Автопривязка и доступ — независимые операции.** Для нового импорта предлагается:

1. Сервис проверяет всю разрешённую границами установки базу, включая записи,
   скрытые от импортирующего сотрудника; интерфейс получает только допустимый
   итог. Не расширять доступ между сайтами/организациями установки.
2. Автопривязка допустима по проверенному внешнему идентификатору или
   единственному непротиворечивому точному совпадению. ИНН сопоставлять через
   реквизиты и их владельцев; общий подрядчик может быть связан с несколькими
   карточками. Телефон/email могут определить человека, но не выбрать одну
   из нескольких его компаний. Название/домен — кандидаты, не автопривязка.
   При разных совпадениях по полям — ручной разбор без создания нового дубля.
3. Если компания чужая, однозначную связь сохраняет системная операция, а
   новую продажу получает её ответственный. Импортёр остаётся инициатором;
   ему доступен итог строки «передано ответственному», а не карточка компании.
   Сама загрузка не меняет закрепление, контакты и реквизиты существующего клиента.
4. Запрос нужен, когда импортёр хочет сам работать с этой продажей: запрашивается
   делегирование конкретной продажи, а не обязательный доступ ко всей компании.
   До решения работа идёт у ответственного; повторные запросы объединяются.
   Если ответственного нет — назначение по правилам очереди/руководителем.
5. В режиме рассылки чужая компания исключается из личной кампании с причиной.
   Централизованная рассылка требует отдельного полномочия на аудиторию;
   загрузка файла такого полномочия не даёт. Не создавать тысячу запросов
   доступа автоматически; групповой разбор доступен уполномоченному сотруднику.

**Когда создавать продажу после рассылки.** Отправка, открытие письма и просмотр
презентации сохраняются как события кампании. Даже отфильтрованный просмотр
не подтверждает потребность. По настройке он может создать одно напоминание
ответственному с защитой от повторов, но не сделку. Заявка «Рассчитать стоимость»,
запрос звонка по услуге или подтверждённый интерес запускают проверку клиента
и открытого обсуждения; обычный ответ «не пишите», автоответ или вопрос поддержки
не создаёт продажу. Менеджер может явно начать конкретную исходящую продажу,
не дожидаясь ответа; это осознанное действие, а не побочный эффект импорта.

Пример: 1000 строк файла → до 1000 адресатов после проверки, повторов и
исключений → события просмотра → реальные обращения → продажи.
Условно: 100 просмотров, 12 отдельных запросов, 3 продажи — это 12 возможностей,
а не 1000 сделок и не 100 сделок. Числа иллюстративные; несколько сообщений
по одному запросу считаются одной возможностью. Отчёт кампании и воронка
продаж имеют разные знаменатели, связываются через источник обращения.

6. **П4 — услуги, `cms` + интеграция `cms-shop`.** Добавить происхождение и
   изменения условий, связь с позициями заказа; проверить разовый сайт,
   хостинг, первый уже оплаченный период, продление и повтор события.
   Сохранить клиентские доступы У1–У2. П3/П4 можно готовить после П2а,
   но совместный финансовый договор должен быть определён на П1.
7. **П5б/П6 — потребители и переключение.** КП, сообщения/чаты, источники
   записей, задачи, телефония, уведомления, кабинет, фильтры списков, отчёты
   и MCP/REST получают согласованные названия и семантику. Технические
   `lead`/`deal` не менять местами. Сначала совместимые расширения, затем
   перенос данных с журналом, потом переключение интерфейса. Откат не должен
   удалять новые продажи или терять проведённые платежи.

Приёмка импорта отдельно проверяет: известный свой клиент; чужой клиент;
один человек в двух компаниях; конфликт ИНН и email; новая потребность со
старым email; повтор одной заявки; повтор запуска и загрузка того же файла;
отписанный контакт; тысяча холодных строк без сделок; просмотр без сделки;
подтверждённый интерес с одной сделкой. Проверять утечки через предпросмотр,
экспорт, списки, КП, поиск и уведомления, а не только открытие карточки.
Исторические холодные лиды сначала классифицируются на копии базы: при наличии
задач, переписки, КП или партнёрских начислений автоматическое удаление запрещено.

## Повторы клиентов, закрепление и импорт базы

Целевые правила от 27.10.2026, реализация не начата. Заменяют прежнее решение
от 26.10.2026 «лид только для нового клиента». Здесь «сделка» — продажная
сделка на основе нынешнего `CmsLead`, «услуга» — нынешний `CmsDeal`.

**Два вида повторов.** Компания/человек — постоянная карточка; сделок у них
может быть несколько. Отдельно проверять повтор клиента и повтор конкретного
обращения. Новая потребность существующего клиента разрешает новую сделку;
продолжение того же открытого обсуждения относится к существующей. Закрытую
попытку не переоткрывать автоматически из-за попадания контакта в рассылку.

**Общая проверка по базе.** Email, телефон, ИНН, домен и название используются
для поиска кандидатов, включая недоступные сотруднику записи. Название и
совпадение отдельных контактов не являются безусловным основанием слияния.
Одна операция проверки используется формами, импортом и API; проверка не
выдаёт права чтения чужой карточки. Неизвестное обращение можно принять с
контактом без выдуманной компании; связь уточняется при разборе.

**Недоступный клиент.** Показывать минимальный ответ «Такой клиент уже есть,
ответственный …», без чужих контактов, переписки и сумм. Действия — запросить
доступ/передачу, отказаться или указать «Это другая компания» с причиной и
отметкой возможного дубля. Объединение доступно уполномоченному сотруднику,
с сохранением истории, связей, согласий и запретов и записью результата.

**Ответственность.** По умолчанию новую сделку получает ответственный компании,
инициатор сохраняется отдельно. Можно поручить другому менеджеру конкретную
сделку без передачи всей компании; ему доступны только явно разрешённые
контакты и материалы этой продажи. Это права сотрудников, не роли клиента
У1–У2. Неотработанная сделка может возвращаться в общий пул по настраиваемому
сроку; действующий клиент с обслуживанием автоматически не освобождается
только из-за отсутствия новых продаж. Точные сроки задать при реализации.

**Импорт холодной базы и заявок.** Не создавать отдельную сущность человека
поверх существующих контактов; выбрать существующую карточку или создать
компанию/контакт с источником и состоянием обработки. Холодная база — аудитория,
а не скрытая стадия продажной сделки. Конкретное хранение состояния аудитории
уточнить на П1; текущий `LeadImport` сам по себе пока не реализует этот план.

| Нашли / получили | Целевое действие |
|---|---|
| Действующий клиент | Использовать существующую карточку; не включать автоматически в холодную аудиторию; допродажи — отдельная подходящая аудитория |
| Бывший клиент, партнёр, поставщик | Использовать существующую компанию/контакт, сегментировать и проверить допустимость обращения |
| Открытая сделка по тому же запросу | Дополнить её, не создавать повтор; учитывать текущую работу менеджера при рассылке |
| Отказ с действующей паузой или запрет контакта | Исключить в соответствующей теме/канале/сроке; импорт не снимает ограничений |
| Давний отказ | При допустимости включить контакт в аудиторию; закрытую сделку не переоткрывать; новый интерес — новая попытка продажи |
| Новый холодный контакт | Создать/уточнить карточку контакта или компании, источник и состояние аудитории; сделку не создавать |
| Импорт реальной заявки или подтверждённый новый интерес | Найти клиента и повтор запроса, затем создать сделку либо дополнить открытую |

Отклик для новой сделки — конкретный интерес: ответ, заявка, просьба связаться,
подтверждённая потребность в разговоре. Менеджер также может явно начать работу
над конкретной продажей. Открытие письма, переход и просмотр презентации —
сигналы, они сами сделку не создают; задача связаться может остаться отдельным
правилом. Поддержка по действующей услуге становится задачей, не продажей.

**Отказ и паузы.** «Не сейчас» — пауза по потребности до даты; «эта услуга не
нужна» — ограничение по теме; «не пишите» — запрет рекламных обращений по
соответствующему контакту/каналу. Причина отказа не должна автоматически
блокировать все услуги клиента на один общий срок. Согласия и отписки остаются
у контакта и проверяются общим механизмом коммуникаций.

## Рассылки и КП

- Рассылка создаёт обычные сообщения пачкой (`ChunkedJobHandler`), каждое в
  ленте своего лида; получатели фиксируются при запуске и только из видимых
  менеджеру; сводка исключённых и предпросмотр перед запуском; пауза, отмена,
  отчёт. Стоп-лист при любой отправке, ссылка «отписаться» и
  `List-Unsubscribe`, согласие для рекламы (38-ФЗ).
- Ящик рассылок (например promo@) — обычный ящик с правами, но отправка через
  API сервиса (Unisender Go и аналоги, транзакционная отправка с нашим id в
  метаданных и событиями доставки по вебхуку); приём ответов — IMAP или
  `Reply-To` на рабочий ящик. Домен настроить (SPF, DKIM), отключить пиксели и
  подмену ссылок для личных КП.
- «Открыто» по пикселю ненадёжно; надёжный сигнал — просмотр КП на нашей
  странице, см. «КП (реестр предложений)». Рассылка КП на 100 лидов — это
  100 отправок КП, у каждой своя ссылка.

**Схема рассылок** (согласовано с владельцем 23.10.2026, этап 4).

- **Кампания** — сущность `cms-communication`: аудитория (лиды или компании по
  фильтру либо импорт), содержание, канал, расписание, отчёт. Получатели
  фиксируются при запуске; каждая отправка — отдельное сообщение в ленте
  своего лида, у каждой своя личная ссылка.
- **Два вида содержания**:
  1. «Рассказать о решении» (например `/solutions/plitka`,
     `/works/sfery/plitka`): письмо по шаблону с подстановками и одной
     Презентацией на всех (у каждого получателя своя личная ссылка);
     позиций нет. Открытие — запись «открыл предложение» в ленте лида (учёт
     через страницу-переход, см. «Единый реестр «Предложения»»). Ответ
     приходит в рабочий ящик и привязывается к лиду. Открывшему — задача
     менеджеру «позвонить» (правило «задача при первом открытии» по
     настройке кампании).
  2. «КП каждому»: шаблон КП (`cms-proposal`); при запуске каждому лиду
     автоматически создаётся его КП из шаблона и отправляется. Дальше — как
     обычное КП: просмотр, «Принять», «Задать вопрос». Вручную КП никто не
     создаёт.
  В обоих случаях кампания отправляет предложение из единого реестра
  «Предложения» через «Отправить клиенту», с кодом на каждую отправку.
- **Получатели только из CRM**: иначе некуда записать отправку, открытие и
  ответ. Импорт списка (таблица/CSV) с проверкой повторов
  (`cms_company_duplicate_check` и аналог для лидов), источником «Рассылка»,
  отметкой о согласии и её основанием. Стоп-лист и «отписаться» — при любой
  отправке кампании.
- **Каналы кампании**:
  - малые объёмы (десятки писем) — ящик менеджера как обычные личные письма
    с ограничением скорости (по умолчанию не больше ~30 в день с ящика,
    паузы между письмами); ответы приходят сами;
  - сотни и тысячи по своей базе с согласием — сервис рассылок (Unisender Go
    и аналоги) через API, события доставки и отписки по вебхуку, ответы — в
    рабочий ящик через `Reply-To`.
- **Холодные рассылки** (база собрана самостоятельно, согласия нет): сервисы
  рассылок (Unisender) их запрещают и блокируют аккаунт; 38-ФЗ требует
  предварительного согласия на рекламную рассылку. Поэтому через сервис —
  только своя база с согласием. Холодные контакты — только небольшими
  персональными письмами от менеджера, по возможности с отдельного домена
  (не портить репутацию основного), с отпиской и стоп-листом; кампания
  помечает получателей без согласия и не даёт отправить их через сервис.

**Списки получателей** (согласовано с владельцем 24.10.2026, этап 4, пункт
4D; как «Списки» и «Сегменты» Unisender, но внутри CRM). Пример владельца:
компании сферы «Плитка», у которых нет оплат (ещё не работают с нами), плюс
какие-то лиды, плюс что-то ещё — и по этому списку рассылка.
- **Участник списка — запись CRM, не адрес**: компания, человек компании,
  лид, клиент. Контакт выбирает канал при отправке: письмо — email, СМС —
  телефон, Telegram и MAX — привязанный чат бота. Поэтому один список служит
  всем каналам. Согласие и отписка остаются у контакта (4A): отписанный
  участник остаётся в списке, при отправке исключается с причиной.
- **Наполнение**: вручную («Добавить в список» в карточке); массовое действие
  «Добавить в список рассылки» в разделах «Компании», «Лиды», «Клиенты»
  поверх их стандартных фильтров (отмеченные или все по фильтру) — своего
  конструктора фильтров не делаем; импорт сразу в список; ИИ через MCP тем же
  сервисом. У участника видно, кто, когда и откуда его добавил.
- **Правила списка** — сохранённые условия (фильтр раздела CRM: например
  «Компании: сфера Плитка, нет оплат»), несколько правил объединяются.
  Режимы списка: «Постоянный» (только добавленные), «Автопополнение»
  (правила пересчитываются при каждой отправке), «Обновить по кнопке»
  (перед отправкой показывает, кто добавится и кто выпадет, состав
  фиксируется по подтверждению). Вручную убранный участник по правилу не
  возвращается. Перед реализацией проверить, можно ли хранить правило как
  сохранённый фильтр стандартного раздела (`cms-backend`) и считать его через
  тот же запрос и `forManager()`, что и в разделе.
- **Кампания**: аудитория — один или несколько списков, «исключить списки»
  (например, «действующие клиенты») и канал; сводка перед запуском — как
  сейчас (нет контакта для канала, отписан, нет ящика). Получатели по одному
  с личными письмами (4B, ИИ) дополняют аудиторию; фильтр лидов в форме
  кампании позже становится правилом списка.
- **Нужно в ядре**: в разделе «Компании» есть фильтр по сферам (категориям) и
  «Готовый фильтр» «Есть неоплаченные счета», но нет «Нет оплат» (ещё не
  клиент) — добавить его в `skeeks/cms` (оплаты `cms-shop`, если установлен).
- С Unisender списки не синхронизируются: источник правды — CRM, сервис
  рассылок только отправляет; при необходимости — выгрузка списка в CSV.
- **Правило списка из двух частей** (согласовано 24.10.2026): фильтр
  раздела CRM (ядро: сфера, статус, город, ответственный, «нет оплат») и
  условия общения, которые добавляет `cms-communication` (ядро о письмах не
  знает):
  - давность: не писали N дней (ни одного нашего письма, личного или
    рассылки); не было никакого контакта N дней (письмо, звонок, СМС);
    последний входящий от клиента старше N дней; не получал рассылок темы N
    дней;
  - реакция: открывал предложение, но не ответил; получал, но не открывал;
    отвечал на рассылку; уже получал это предложение или Презентацию;
    состоит / не состоит в другом списке;
  - возможность: есть контакт для канала; есть согласие по теме; адрес
    личный или общий (info@, sales@);
  - деловые (частично фильтры ядра): нет оплат или последняя оплата старше
    N дней; сумма оплат за период; нет активной сделки и открытых задач;
    есть или нет услуг у нас (`cms-hosting`, если установлен).
- **Защита всех рассылок** (шаг 1 списков): частота на контакт — не больше
  одного рекламного письма раз в N дней по всем кампаниям (настройка сайта,
  в сводке причина «Недавно получал рассылку»); «одна компания — одно
  письмо» (компания и её люди в аудитории — пишем основному или выбранному
  контакту, переключатель кампании); не мешать менеджеру — исключать тех, с
  кем общались за последние N дней.
- **Удобства списка**: счётчики (участники, можно отправить каждым каналом,
  отписанные, без контакта), история участника (кто, когда, откуда добавил,
  какие кампании получил), тестовый список своих адресов, выгрузка в CSV.
- **Позже**: проверка двух вариантов темы на части аудитории с отправкой
  остальным лучшего; метки ИИ после разбора базы («устаревший сайт», «нет
  мобильной версии») как условие правила.

**Служебные и рекламные сообщения, темы, согласие, отписка** (согласовано с
владельцем 23.10.2026, этапы 4 и 7).

| | Служебные | Рекламные (рассылки) |
|---|---|---|
| Примеры | счёт заканчивается, услуга истекает, КП по запросу, ответ по задаче | новое решение, акция, новости студии, холодное предложение |
| Этап | 7 «Уведомления клиентам» | 4 «Рассылки» |
| Согласие | не нужно | нужно (38-ФЗ), кроме холодных писем менеджера |
| Отписка | нет; клиент выбирает только канал получения | по темам, ссылка в каждом письме и `List-Unsubscribe` |

- **Отписка от рекламы никогда не отключает служебные сообщения.** Личные
  письма менеджера отписка не блокирует, а показывает предупреждение.
- **Темы рассылок** заводятся в настройках («Новые решения и услуги», «Акции
  и скидки», «Новости студии», «Новости платформы»). У каждой кампании одна
  обязательная тема.
- **Согласие и отписка хранятся у контакта** — адреса почты, номера
  телефона, позже чата бота — по каждой теме, а не у лида: один адрес бывает
  у лида, компании и клиента одновременно, а согласие на почту не означает
  согласия на СМС. У согласия — основание («подписался на сайте», «дал
  согласие устно», «нет согласия — холодный контакт»), дата и кто отметил.
- **Отписка относится к контакту, через который пришла рассылка**: ссылка в
  письме отписывает этот адрес, «СТОП» на СМС — этот номер, кнопка бота —
  этот чат. Страница отписки показывает темы галочками (отписаться от одной
  или от всех) и пункт «отписаться от всех рекламных рассылок по всем
  каналам» — тогда отписываются все контакты лида, компании или клиента.
- **В карточке** лида, компании и клиента у контакта видно состояние
  подписки по темам.
- **Кампания перед запуском** показывает исключённых и причину: отписан от
  темы, нет контакта, нет согласия для выбранного канала (для сервиса
  рассылок согласие обязательно).
- **Этап 7** даёт клиенту выбор каналов служебных сообщений на тех же
  контактах, без отписки.

## Отправить клиенту

Согласовано 23.10.2026 (этап 3, мини-сессия A). КП, счета, акты, позже
уведомления этапа 7 отправляются клиенту любым каналом, поэтому отправка — общая
точка `cms-communication`, а не код каждого пакета.

- **Отправляемое** описывает пакет (КП, счёт): название, короткий текст,
  личная ссылка (создаётся на каждую отправку — пакет получает канал и
  получателя и возвращает ссылку со своим кодом), файлы (PDF), запись в CRM, к
  которой относится отправка (лид, компания, сделка, клиент).
- **Окно «Отправить клиенту»**: контакты клиента из CRM (email, телефоны,
  позже привязанные боты), выбор канала и получателя, предпросмотр текста,
  правка текста менеджером. Видимость записей — `forManager()`.
- **Канал сам решает вид**: письмо — текст, кнопка «Открыть …», PDF
  вложением, уходит из ящика менеджера как обычное письмо (лента, переписка,
  «Отправленные»); СМС — короткий текст и ссылка через провайдеров СМС
  `skeeks/cms`; Telegram и MAX — кнопка и файл (этап 5, без переделки
  отправляемого). Канал возвращает созданное сообщение, пакет хранит его в
  своей записи отправки.
- **«Прикрепить из…» в форме письма** («источник вложений»): пакеты добавляют
  пункты («КП», потом «Счёт»); выбранное вставляется в письмо личной ссылкой
  и файлом, а пакет получает отметку об отправке, как из окна «Отправить
  клиенту».
- Ограничение получателей стенда (`allowedRecipients`) действует для всех
  каналов, для СМС — свой список номеров.

## КП (реестр предложений)

Согласовано 23.10.2026 (этап 3). Пакет `skeeks/cms-proposal`.

**Берём готовое**: позиции и итоги как у счёта `cms-shop` (`ShopBillItem`:
наименование, единица, количество, цена, скидка, сумма, `vat_name`, НДС не
считается — только надпись); PDF через mPDF, как счёт и отчёт по задаче,
оформление — шаблон документов сайта `CmsDocumentTemplate` (логотип, цвета,
тема); страница по секретному коду без входа, как у счёта; создание из лида,
сделки, компании — `Skeeks::$recordSources` (`?source=`); лента —
`logRenderers`, уведомления — `CmsWebNotify`; реквизиты нашей компании
копируются в версию, как в счёт (`fillContractorSnapshot`).

**Модель**:
- КП — номер, название, клиент (лид, компания или сделка — любой из трёх;
  КП лида видны в карточке его компании), ответственный, статус (черновик,
  отправлено, открыто, принято, отклонено, истекло), срок действия (по
  умолчанию 14 дней), валюта, текущая версия.
- Версия — содержимое: вступление и условия (общий редактор текста, картинки
  можно), позиции с разделами, итог и скидка, реквизиты. Отправленная версия
  не меняется: правка после отправки создаёт новую версию. PDF версии
  делается при первой отправке и хранится с ней.
- Позиция — как строка счёта, с необязательной ссылкой на товар/услугу
  `cms-shop`, если пакет установлен.
- Отправка — версия, канал, получатель, сообщение CRM, секретный код ссылки,
  кто и когда отправил, первый и последний просмотр, число просмотров.
- Просмотр — время, отправка, браузер (для истории и отсева роботов).
- Шаблоны КП — готовые наборы текста и позиций («Сайт под ключ», «SEO»,
  «Хостинг»); новое КП делается из шаблона.

**Страница КП для клиента**: позиции, итог, условия, «Скачать PDF»,
«Принять», «Задать вопрос». Ссылка показывает отправленную версию; если
отправлена более новая — плашка «Есть обновлённое предложение». После срока —
«Предложение истекло, свяжитесь с менеджером». «Принять» меняет статус,
пишет в ленту, уведомляет менеджера; счёт автоматически не создаётся —
менеджер выставляет его кнопкой «Выставить счёт» (позиции переносятся в
счёт `cms-shop`). «Задать вопрос» создаёт сообщение в переписке клиента: входящее «Сообщение
с сайта» без ящика (`services\SiteMessages`, канал `site`, переписка
`site:proposal:<id>`), связанное с клиентом КП и его компанией; ответ —
обычным письмом на адрес, куда отправляли КП.

**Честное «открыто»**: почтовые проверки ссылок, предпросмотр Telegram и MAX,
антивирусы открывают ссылку раньше клиента. Просмотр засчитывается только
сигналом из самой страницы после её показа в браузере; известные роботы
предпросмотра не считаются. Первый просмотр — запись «КП открыто» в ленте и
уведомление менеджеру.

**В CRM**: раздел «КП» (список, фильтры по статусу и менеджеру), блок «КП» в
карточках лида, компании и сделки с кнопкой «Создать КП», записи ленты «КП
отправлено (канал)», «КП открыто», «КП принято».

**Отложено**: блоки «О нас», кейсы и портфолио внутри КП; электронная
подпись; расчёт НДС.

**Необязательные позиции и выбор клиента** (согласовано 23.10.2026, этап 3,
шаг D). Позицию или раздел КП можно отметить «на выбор клиента» (включено или
выключено по умолчанию). На странице КП клиент включает и выключает их
галочкой, итог пересчитывается сразу; в итоге и PDF видно, что входит, а что
предлагается дополнительно. «Принять» сохраняет выбранный вариант в отправке
(состав и сумма на момент принятия), он виден в карточке КП и в ленте
(«КП принято: с продвижением»). Сама версия не меняется. «Выставить счёт»
переносит в счёт только выбранные позиции.

**Единый реестр «Предложения»: КП и Презентация** (согласовано с владельцем
23.10.2026, этап 3, шаг E; заменяет прежнюю идею отдельного отправляемого
«страница сайта» в `cms-communication`). Нам важен факт открытия нашей
личной ссылки; что показать после — дело вида предложения. Поэтому одна
сущность `cms-proposal` с видом:

| Вид | Что внутри | Что видит клиент по ссылке |
|---|---|---|
| КП | позиции, версии, итог, условия, «Принять», «Задать вопрос» | страница КП |
| Презентация | адрес страницы (своего сайта или любой, например `/works/sfery/plitka`, `/solutions/plitka`) и короткий текст менеджера | страница-переход: засчитывает просмотр и сразу переводит на страницу |

Отправка, личные ссылки, отправки по каналам, учёт просмотров, лента,
уведомления, правила и кампании этапа 4 — общие для обоих видов. Менеджер:
«Создать предложение» → вид → «Отправить клиенту». Кампания всегда
отправляет предложение: каждому лиду своё КП из шаблона или одну и ту же
презентацию.

Оговорки:
1. **Своя форма у каждого вида.** Вид выбирается первым; у Презентации нет
   позиций, версий и «Принять» — только адрес, название, текст менеджера
   (срок действия по желанию). Пустых полей КП в ней не показывать.
2. **Адрес перехода хранится в предложении**, никогда не берётся из
   ссылки: страница-переход не должна стать открытым перенаправлением
   (фишинг от имени нашего домена). Разрешённые адреса — `http(s)`; чужие
   домены допустимы, но сохраняются только сотрудником.
3. **Метки для Метрики.** При переходе к адресу добавляются
   `utm_source=crm`, `utm_medium=<канал>`, `utm_campaign=<номер предложения
   или кампании>` (не затирая уже указанные метки), иначе визиты выглядят
   прямыми заходами.
4. **Отсев проверок ссылок.** Просмотр засчитывается сигналом из страницы
   после её показа (роботы предпросмотра без скриптов не засчитываются и
   никуда не переходят). Защитные системы, которые открывают ссылку в
   настоящем браузере (проверка ссылок Outlook и подобные), отсеиваются по
   признакам: открытие в первые секунды после отправки, адреса
   дата-центров, известные браузерные отпечатки. Такое открытие в ленте
   помечается «возможно, проверка ссылок», статус «открыто» и уведомление
   оно не даёт.
5. **Кнопка «Связаться» на целевой странице — позже.** После перехода на
   `/works/sfery/plitka` у клиента нет «Задать вопрос»; пока менеджер
   звонит по уведомлению или задаче. Следующий шаг (вне этапа 3): на наших
   сайтах запоминать код перехода, показывать «Связаться с менеджером» и
   писать в ленту лида, что он смотрел дальше.

**Правило «задача менеджеру при первом открытии»** (согласовано
23.10.2026, этап 3, шаг E). При первом засчитанном открытии предложения
любого вида ответственному ставится задача «Позвонить: клиент открыл
предложение №…» на сегодня (вне рабочего времени — на ближайший рабочий
день), привязанная к лиду/компании/сделке и к предложению. Включается
настройкой (по умолчанию включено для отправок менеджером, для кампаний —
настройкой кампании). Повторные открытия задачу не создают; если у
ответственного уже есть открытая задача по этому предложению — не создаётся
новая. Открытия, помеченные «возможно, проверка ссылок», задачу не ставят.
Сделано так (шаг E): правило срабатывает на первом засчитанном просмотре
каждой отправки, поэтому новая отправка, открытая после выполненной задачи,
даёт новую задачу; метка кампании в адресе — `utm_campaign=proposal-<номер>`
(у кампаний этапа 4 будет `campaign-<id>`).

**Сценарий: звонок → презентация → КП** (согласовано 23.10.2026). Так
менеджеры работают с готовыми решениями.
1. После звонка менеджер отправляет клиенту Презентацию (страница решения
   или сферы, например `/works/sfery/plitka`): общую, созданную один раз
   для всех, или созданную для этого клиента. Письмо как
   сейчас, но ссылка личная: в ленте видно, открыл ли клиент и когда, при
   открытии менеджеру ставится задача «Позвонить».
2. Если клиент заинтересовался — КП из шаблона решения («Сайт для магазина
   плитки»): во вступлении кнопка «Подробнее о решении» на страницу решения
   (описание не повторяется), основные позиции — сайт, «Продвижение» —
   необязательный раздел, который клиент включает сам (шаг D).
3. «Принять» фиксирует выбранный вариант, менеджер выставляет счёт на него.

## Стенд skeeks.com (Windows)

- Пакеты стоят из боевого `composer.lock`, а `link-shared-vendor.php`
  заменяет их ссылками на общий вендор: правки в
  `C:\SkeekS\dev\php\vendor\skeeks\cms-communication` сразу видны стенду
  (быстрый профиль и Compose Watch). Новые миграции — `cms/migrate`, затем
  очистка `frontend/runtime/cache`; после правки задач — перезапуск
  `worker-communication`.
- Обработчик очереди — сервис `worker-communication` в `compose.fast.yaml`.
  Расписания на стенде нет: письма забираются кнопкой.
- `docker/config/main-dev.php`: ключ шифрования стенда и
  `communication.allowedRecipients = ['@skeeks.com']` (база — копия боевой).
  После правки — `docker compose -f compose.yaml -f compose.fast.yaml restart worker-communication`.
- Тестовый ящик — sem-ov2007@yandex.ru (пароль приложения вводит владелец).
  Для проверки уведомлений у пользователя 1 на стенде есть строка прав
  «все письма» на этот ящик (22.10.2026).
